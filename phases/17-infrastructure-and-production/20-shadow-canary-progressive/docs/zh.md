# LLM 的流量镜像、金丝雀发布与渐进式部署

> LLM 的发布结合了软件部署中最困难的部分：没有单元测试、故障模式分散、信号延迟。流程为：(1) 影子模式（Shadow Mode）——将生产环境的请求复制到候选模型，记录日志并进行对比，对用户零影响；能捕获明显的分布问题，但不能作为质量保证；(2) 金丝雀发布（Canary Rollout）——逐步转移流量 10% → 25% → 50% → 75% → 100%，每一步设置检查点（Gates）；跟踪延迟百分位、单次请求成本、错误/拒绝率、输出长度分布、用户反馈率；(3) 在确认稳定性后，对差异显著的替代方案进行 A/B 测试。非确定性是不可避免的——由于 GPU 浮点数运算的非结合性以及批次大小差异，相同输入在不同运行中准确率波动可达 15%。成本是变量而非常量——性能提升 20% 的模型，单次调用成本可能高出 3 倍。回滚速度至关重要：如果回滚需要重新部署，说明你太慢了。策略配置于配置文件/特性开关中；模型托管于注册表并固定了摘要（digest）；回滚操作 = 切换策略 + 重置阈值 + 固定旧模型版本，整个过程仅需数秒。

**类型：** 学习
**语言：** Python（标准库，简易金丝雀进度模拟器）
**前置知识：** 第 17 阶段 · 13（可观测性），第 17 阶段 · 21（A/B 测试）
**预计时间：** 约 60 分钟

## 学习目标

- 区分影子模式（零影响对比）、金丝雀发布（实时流量渐进式）和 A/B 测试（稳定性确认后的对比）。
- 列举五个针对 LLM 的金丝雀指标（延迟、单次请求成本、错误/拒绝率、输出长度分布、用户反馈）。
- 解释为什么 LLM 的非确定性（高达 15%）会改变发布过程中“稳定”的含义。
- 设计一个只需数秒（切换策略）而非数小时（重新部署）的回滚路径。

## 问题所在

你上线了一个新模型。离线评估显示准确率提升了 3%。你在生产环境中将其开启。24 小时内，成本上升了 40%，用户踩（thumbs-down）比例增加了 8%，三个客户工单报告“回答很奇怪”。你执行了回滚。重新部署耗时 3 小时。你的周末彻底毁了。

上述每一个环节本都可避免。影子模式会在任何用户看到之前捕获那 40% 的成本飙升。金丝雀发布会在踩的比例发生变化时停留在 10%。基于策略开关的回滚只需 30 秒。正是这种纪律性填补了“离线评估看起来不错”与“真实用户感到满意”之间的鸿沟。

## 核心概念

### 影子模式（Shadow Mode）

候选模型接收与生产环境相同的请求；输出结果仅记录日志，不返回给用户。对用户零影响。需记录：

- 输出内容（与生产环境输出进行对比）。
- Token 数量（成本差异）。
- 延迟。
- 拒绝情况与错误。

能捕获：成本激增、长度退化、明显的拒绝逻辑变化、严重错误。**无法捕获**：用户能感知到的质量差异。影子模式是一种冒烟测试，而非质量测试。

### 金丝雀发布（Canary Rollout）

逐步转移流量并设置检查点（Gates）。典型推进比例为：1% → 10% → 25% → 50% → 75% → 100%。每一步基于以下 5 个指标设置检查点：

1. **延迟百分位** —— P50、P95、P99。触发条件：金丝雀版本的 P99 延迟超过基线的 1.5 倍。
2. **单次请求成本** —— 综合成本（$）。触发条件：高于基线 20% 以上。
3. **错误/拒绝率** —— 5xx 状态码及显式拒绝。触发条件：达到基线的 2 倍。
4. **输出长度分布** —— 均值 + P99。触发条件：发生分布偏移。
5. **用户反馈率** —— 踩/提交工单。触发条件：达到基线的 1.5 倍。

### 非确定性是新常态的方差

相同的输入会产生不同的输出。原因包括：

- GPU 浮点数运算的非结合性（浮点数归约顺序随批次不同而变化）。
- 批次大小差异（同一提示词在 128 的批次中与在 16 的批次中表现不同）。
- 采样机制（温度参数 temperature > 0）。

实测数据表明：在相同的评估集上，连续运行的准确率波动可达 15%。发布过程中的“稳定”意味着指标处于预期方差范围内，而非与基线完全一致。因此，检查点的阈值应设置在噪声底限之上。

### 成本是变量

性能提升 20% 的模型，单次调用成本可能高出 3 倍。“单次请求成本”是五大检查点之一。如果一个“更好”的模型破坏了单位经济效益，则属于必须回滚的情况。

### 回滚是终极武器

- 策略开关（特性开关系统）：在配置中切换百分比；耗时数秒。
- 模型固定（注册表摘要）：被固定的模型不会自动升级。
- 回滚操作 = 恢复开关 + 将固定摘要设为上一版本。耗时数秒，而非数小时。

如果你的技术栈需要重新部署才能回滚，请在正式发布前修复该问题。

### 工具链

**Argo Rollouts** / **Flagger** —— Kubernetes 渐进式交付控制器。可与 Istio/Linkerd 加权路由集成。

**Istio 加权路由** —— 服务网格层面的流量拆分。

**KServe / Seldon Core** —— 内置金丝雀功能的模型推理服务。

**特性开关（Feature Flags）** —— LaunchDarkly、Flagsmith、Unleash。支持策略级切换，无需重新部署。

### 指标检查频率

金丝雀检查点的检测频率为每 5-15 分钟一次，具体取决于流量规模。1% 的流量配合 10 req/min 的请求速率，每个窗口期可获得 50-150 个数据点——这对延迟指标足够，但对用户反馈而言噪声较大。10% 的流量可提供约 10 倍的样本量。各阶段的推进应暂停足够长的时间，以便在每个步骤积累足够的样本。

### A/B 测试步骤为可选

如果新模型具有显著差异（行为模式、成本曲线或语气风格不同），则在金丝雀发布通过后，以 50% 的流量进行 A/B 测试。如果仅仅是性能改进版，则在金丝雀检查点全部通过后直接推进至 100%。

### 关键数字（务必牢记）

- 金丝雀推进比例：1% → 10% → 25% → 50% → 75% → 100%。
- 非确定性上限：相同输入下连续运行的波动可达 15%。
- 五大金丝雀指标：延迟、成本、错误/拒绝率、输出长度、用户反馈。
- 成本检查点：高于基线 20% 即视为触发。
- 回滚：数秒完成，而非数小时。

## 核心术语

| 术语 | 常见说法 | 实际含义 |
|------|----------|----------|
| Shadow mode（影子模式） | “复制到新模型” | 零影响地将请求发送至候选模型用于记录日志 |
| Canary（金丝雀发布） | “渐进式流量” | 逐步向用户暴露的发布流程，附带检查点拦截 |
| Gates（检查点） | “发布检查” | 阻止进一步推进的指标阈值 |
| Non-determinism（非确定性） | “LLM 方差” | 不可消除的连续运行差异 |
| Policy flag（策略开关） | “开关回滚” | 配置级别的回滚，耗时数秒而非数小时 |
| Model pin（模型固定） | “注册表摘要” | 指向特定模型版本的不可变引用 |
| Argo Rollouts | “K8s 渐进式” | 原生支持 Kubernetes 的金丝雀/回滚控制器 |
| KServe | “K8s 推理” | 内置金丝雀原语的模型推理服务 |
| Istio weighted（Istio 加权） | “网格拆分” | 服务网格流量分发器 |
