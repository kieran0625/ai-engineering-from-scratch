# 面向前缀密集型负载的 SGLang 与 RadixAttention

> SGLang 将 KV 缓存视为一等公民的可复用资源，并存储于基数树中。当 vLLM 采用 FCFS（先来先服务）调度请求时，SGLang 的缓存感知调度器会优先处理共享前缀更长的请求——这本质上是一种深度优先的基数树遍历策略，以确保热点分支常驻在 HBM 中。在 Llama 3.1 8B 模型上，使用类 ShareGPT 的 1K 提示词时，SGLang 达到约 16,200 tok/s，而 vLLM 约为 12,500，优势约为 29%。在前缀密集型的 RAG 负载下，该优势可达 6.4 倍。在语音克隆类负载下，缓存命中率超过 86%。截至 2026 年，已在 xAI、LinkedIn、Cursor、Oracle、GCP、Azure、AWS 等平台的 40 万+ GPU 上部署。这里的陷阱在于，如果前缀顺序不一致，6.4 倍的性能优势就会消失——顺序控制是工程师的关键杠杆。

## 学习目标

- 绘制 RadixAttention 原理图：说明前缀如何在基数树中存储，以及以同一分支为根的不同序列如何共享 KV 块。
- 解释缓存感知调度机制，并说明为何 FCFS 不适用于前缀密集型流量。
- 根据前缀缓存命中率和提示词长度分布，计算工作负载的预期加速比。
- 指出能让 6.4 倍性能提升成为现实而非错失机会的提示词排序规范。

## 问题所在

传统推理系统将每个请求的提示词视为不透明整体。即使有 5,000 个 RAG 请求都以相同的 2,000 token 系统提示词加上相同的检索前言开头，vLLM 仍会重复预填充这 2,000 token 的前缀 5,000 次。GPU 在不断重复执行相同的工作。

核心观察：在智能体和 RAG 工作负载中，提示词几乎总是共享很长的前缀。系统提示词、工具模式、少样本示例、检索头部、对话历史——这些内容都会在请求间重复出现。如果你只为该前缀存储一次 KV 缓存并重用它，就无需再次进行预填充。

RadixAttention 正是为此设计。Token 在基数树中进行索引；每个节点拥有从根节点到该节点路径上 Token 序列对应的 KV 块。新请求进入时会遍历这棵树：任何匹配的节点都会复用其已有的 KV 块。预填充成本仅与“新增”的后缀部分成正比，而非整个提示词。

挑战在于调度。如果有两个请求共享 2,000 token 的前缀，而第三个请求仅共享其中 200 token，你希望将这两个长共享请求一起处理，以便让长前缀保留在 HBM 中。FCFS 的做法恰恰相反——它优先处理先到达的请求，这可能导致在下一个长前缀请求到来之前，热点分支就被换出。

## 核心概念

### 作为 KV 索引的基数树

基数树（compact trie）用于存储 Token 序列。每个节点拥有一个 Token 范围及其对应的已计算 KV 块。子节点通过追加一个或多个 Token 来扩展序列。

```
root
 |- "You are a helpful assistant..."  (2,000 tokens, 124 KV blocks)
      |- "Context: <doc A>..."        (500 tokens, 31 blocks)
           |- "Question: Alice..."    (80 tokens, 5 blocks)
           |- "Question: Bob..."      (95 tokens, 6 blocks)
      |- "Context: <doc B>..."        (520 tokens, 33 blocks)
```

一个新请求包含系统提示词 + “Context: <doc A>” + “Question: Carol”。调度器进行遍历：系统前缀匹配（复用 124 个块），doc-A 分支匹配（复用 31 个块），然后仅为“Question: Carol”分配全新的块（4 个块）。预填充成本：仅需 4 个新 Token 块。若无此树结构：需 160 个块。预填充成本降低约 40 倍。

### 缓存感知调度

如果缓存频繁置换，基于基数树的复用将毫无意义。关键在于两条调度策略：

1. **深度优先派发**。从队列中选择下一个请求时，优先选择与当前运行集处于同一分支的请求。这能确保热点分支保持驻留。
2. **基于分支级别的 LRU，而非块级别**。淘汰整个分支（从使用时长最短的叶子节点开始），而不是单独淘汰块，从而使缓存结构与基数树结构保持一致。

FCFS 违反了上述两点。一个共享 2,000 token 的请求可能排在一个仅共享 50 token 的请求之后，结果为了容纳那个 50 token 的请求，2,000 token 的分支反而被换出。

### 必须牢记的基准测试数据

- Llama 3.1 8B，H100，ShareGPT 1K 提示词：SGLang 约 16,200 tok/s，vLLM 约 12,500（优势约 29%）。
- 前缀密集型 RAG（相同系统提示词 + 相同文档，不同问题）：SGLang 最高可达 6.4 倍加速。
- 语音克隆负载：前缀缓存命中率达 86.4%。
- SGLang 客户的生产环境命中率：根据提示词规范程度，介于 50% 至 99% 之间。
- 截至 2026 年，已在 40 万+ GPU 上部署。

### 顺序陷阱

6.4 倍的性能提升依赖于一致的提示词模板顺序。如果你的客户端在某些请求中将提示词构造为 `[system, tools, context, history, question]`，而在另一些请求中构造为 `[system, context, tools, history, question]`，基数树就无法找到共享前缀。对人类而言看似共享的前缀，对基数树来说却是两条完全不同的序列。

工程师的杠杆：你的提示词模板就是缓存键。固定顺序。将所有不可变内容（系统提示词、工具、模式）放在最前面。接着放检索上下文。最后放用户问题。切勿将动态内容穿插到前缀中。

来自实际研究的案例：将动态内容移出可缓存前缀，在一次代码变更中就使某次部署的缓存命中率从 7% 跃升至 74%。

### RadixAttention 的优势与劣势

适用场景：
- RAG（相同检索前言，不同问题）。
- 智能体（相同工具模式，不同查询）。
- 带有长系统提示词的聊天场景。
- 带有重复前言的语音/视觉负载。

不适用场景（吞吐量回落至 vLLM 水平）：
- 使用唯一提示词的单次生成任务（代码补全、无系统提示词的开放式聊天）。
- 动态提示词，且每个请求都在前缀中穿插了独特内容。

### 为何这是调度问题，而不仅仅是内核问题

你可以将 KV 复用实现为一个内核层面的技巧。SGLang 的核心洞察在于：只有当调度器能让热点分支保持驻留时，复用才有价值。在混合负载下，简单的“可用即复用”策略会导致缓存频繁置换。正是基于基数树索引的调度器，将这个内核技巧转化为了 29% 的生产环境优势。

### 与 vLLM 的协同关系

两者并非严格的竞争关系。2026 年，vLLM 增加了前缀缓存功能（`--enable-prefix-caching`）和缓存感知路由器（基于 Rust 实现的 vLLM Router）。差距有所缩小但并未完全抹平——SGLang 的全栈架构以基数树为核心；而 vLLM 则是后期嫁接的。对于以前缀复用为主导的负载，SGLang 仍是首选。对于没有强烈前缀模式的通用推理服务，vLLM 依然持平或更优。

## 实践应用

`code/main.py` 实现了一个玩具级的基数树 KV 缓存，以及包含两种策略（FCFS 和缓存感知）的调度器。它将同一工作负载分别通过两种策略运行，报告前缀缓存命中率和吞吐量差异。随后运行一个“乱序排列”的工作负载，以展示 6.4 倍性能优势的崩塌过程。

## 关键术语

| 术语 | 常见说法 | 实际含义 |
|------|----------|----------|
| RadixAttention | “SGLang 的那个东西” | 将 KV 缓存构建为基数树索引，使共享前缀能够复用 KV 块 |
| Radix tree | “紧凑前缀树” | 一种树形结构，每个节点拥有特定 Token 范围及其对应的 KV 块 |
| Cache-aware scheduler | “热点分支优先” | 优先处理与当前驻留分支共享请求的调度器 |
| Prefix-cache hit rate | “你的提示词有多少是免费的” | 从复用 KV 块中服务的提示词 Token 占比 |
| FCFS | “先来先服务” | 破坏前缀局部性的默认调度策略 |
| Branch-level LRU | “淘汰叶子节点” | 与基数树结构相匹配的淘汰策略 |
| Prompt template ordering | “缓存键” | 提示词各组件的顺序决定了基数树能够共享的内容 |
| System prompt pinning | “常驻前缀” | 锁定不可变的系统部分以避免频繁的淘汰抖动 |
