# AI SRE —— 多智能体事件响应、运行手册与预测性检测

> AI SRE 通过 RAG 技术，利用扎根于基础设施数据（日志、运行手册、服务拓扑）的 LLM，自动化实现调查、文档编写与协调阶段。2026 年的架构模式为多智能体编排——由主管智能体协调专业智能体（日志、指标、运行手册）；AI 提出假设与查询，人类负责最终裁量。Datadog Bits AI 与 Azure SRE Agent 已将其作为托管产品发布。运行手册正在演进：NeuBird Hawkeye 采用对抗性评估机制（两个模型独立分析同一事件；结论一致代表高置信度，不一致代表存在不确定性）；操作记忆可在团队更迭中持续保留。自动修复保持谨慎态度：AI 提供建议，人类进行审批。完全自主的操作范围极窄（如重启 Pod、回滚特定部署）且配有严格的安全护栏——任何兜售“一劳永逸”方案的人都在夸大其词。新兴前沿方向：事件前预测。MIT 的一项研究报告指出，一个使用历史日志、GPU 温度与 API 错误模式训练的 LLM，能够提前 10-15 分钟预测出测试集中 89% 的中断事件。行业预测：到 2026 年底，95% 的企业级 LLM 将具备自动故障转移能力。

**前置条件：** 第 17 阶段 · 13（可观测性），第 17 阶段 · 24（混沌工程）
**耗时：** 约 60 分钟

## 学习目标

- 绘制多智能体 AI SRE 架构图：主管智能体 + 专业智能体（日志、指标、运行手册）+ 人工审批关卡。
- 解释为何自动修复的范围是狭窄的（重启 Pod、回滚部署）而非广泛的（重构服务）。
- 命名对抗性评估模式（NeuBird Hawkeye）：两模型一致=高置信度；不一致=升级上报。
- 引用 MIT 89% 早期检测结果及操作约束：没有干预操作的预测只是仪表盘。

## 问题所在

值班工程师凌晨 3 点收到告警：“结账服务错误率飙升。”他们查看 Datadog、Loki、三份运行手册和部署日志。30 分钟后才发现根因是 KV cache 突增导致 vLLM OOM。他们重启了 Pod，错误消除。

到了 2026 年，该调查的前 20 分钟是可以自动化的。按服务分组日志、关联近期部署、匹配运行手册——全部依赖 RAG + 工具调用。一个受监督的智能体可以在人类打开 Datadog 之前完成初步分诊并呈现假设。

完全自主的修复是另一个问题。重启 Pod：安全。扩展 GPU 池：若策略允许则安全。重构服务：绝对不行。核心纪律在于划定这条狭窄的边界。

## 核心概念

### 多智能体架构

```
          Incident
             │
             ▼
        Supervisor
        /    |    \
       ▼     ▼     ▼
  Log agent  Metric agent  Runbook agent
       │     │     │
       └─────┴─────┘
             │
             ▼
        Hypothesis + evidence
             │
             ▼
        Human approval
             │
             ▼
        Action (narrow set)
```

主管智能体将事件拆解为子查询。专业智能体拥有工具访问权限（日志搜索、PromQL、文档检索）。主管智能体进行综合，向人类呈现假设与证据。人类审批或重定向。

### 自动修复范围

**安全（狭窄）**：重启 Pod、回滚特定部署、在预批准范围内扩展池、启用预批准的特性开关。

**不安全（广泛）**：更改服务拓扑、修改资源限制、部署新代码、更改 IAM、修改数据库。

任何兜售“一劳永逸”的人都在夸大其词。随着 AI SRE 的成熟，安全操作集会逐渐扩大，但边界是真实存在的。

### 对抗性评估（NeuBird Hawkeye）

两个模型独立分析同一事件。如果它们对根因达成一致，则置信度高。如果不一致，则将两者假设同时展示给人工进行升级处理。这是一种简单模式，能有效过滤幻觉导致的根因。

### 操作记忆

人员流动是传统 SRE 的无声杀手——团队隐性知识随之流失。AI SRE 将运行手册和事后复盘存储在向量数据库中；每次新事件发生时，智能体会进行检索。当新工程师加入时，AI 已掌握完整的历史记录。

### 事件前预测

MIT 2025 年研究：使用历史日志、GPU 温度、API 错误模式训练的 LLM，能够在测试集上提前 10-15 分钟预测出 89% 的中断事件。

现实检验：没有干预操作的预测只是仪表盘。实际操作问题是“当我们做出预测时，该做什么？”主动排空？发送 Pager 告警？自动扩缩容？答案取决于具体策略。

### 2026 年的产品

- **Datadog Bits AI** —— Datadog 内的托管 SRE 协作者。
- **Azure SRE Agent** —— 原生支持 Azure。
- **NeuBird Hawkeye** —— 对抗性评估 + 操作记忆。
- **PagerDuty AIOps** —— 分诊 + 去重。
- **Incident.io Autopilot** —— 事件指挥官 + 协调。

### 代码化运行手册

运行手册正从 Confluence 页面演变为带有结构化章节（症状、假设、验证、执行）的版本控制 Markdown。结构化的运行手册能提升 RAG 检索效果。启动任何 AI-SRE 落地项目时，都应先将非结构化运行手册转化为结构化格式。

### 需要记住的关键数字

- MIT 早期检测：89% 的中断事件，提前 10-15 分钟。
- 多智能体分诊：主管智能体 +（日志、指标、运行手册）+ 人工。
- 安全自动修复集：重启 Pod、回滚部署、在边界内扩缩容。
- 对抗性评估：两个模型独立运行；一致=高置信度。

## 动手实践

`code/main.py` 模拟了一次多智能体分诊流程：日志智能体发现错误，指标智能体发现 CPU 飙升，运行手册智能体匹配到已知问题。主管智能体对假设进行排序。

## 练习

1. 运行 `code/main.py`。如果日志智能体和指标智能体意见不一致怎么办？主管智能体如何裁决？
2. 为你的服务定义三个“安全”的自动修复操作，并分别说明理由。
3. 编写一份结构化运行手册模板：包含章节、必填字段、验证命令。
4. 预测性检测提前 12 分钟触发。你的策略是什么——发送 Pager 告警、主动排空，还是两者兼有？
5. 论证一个 3 人团队在 2026 年是否应该采用 AI SRE 还是继续等待。请考虑成熟度、事件量与风险。
