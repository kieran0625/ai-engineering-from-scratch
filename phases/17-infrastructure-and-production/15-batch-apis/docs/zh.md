# 批量 API —— 50% 折扣成为行业标准

> 每家主流提供商都推出了异步批量 API，提供 50% 的折扣和约 24 小时的交付周期。OpenAI、Anthropic、Google 以及大多数推理平台（如 Fireworks 的 batch tier、Together batch）都采用了相同的模式。将批量处理与提示词缓存结合使用，可使夜间运行的流水线成本降至同步未缓存成本的约 10%。规则极其简单：只要不是交互式的，就应归类为批量处理。内容生成流水线、文档分类、数据提取、报告生成、批量标注、目录打标——任何能够容忍 24 小时延迟的任务，如果不迁移到批量处理，就意味着白白浪费资金。2026 年的生产实践是将每个新的 LLM 工作负载划分为三个通道：交互式（带缓存的同步调用）、半交互式（带回退机制的异步队列）、批量处理（夜间运行，叠加输入缓存）。那些伪装成交互式但实际能容忍几分钟延迟的工作负载，浪费最为严重。

**类型：** 学习
**语言：** Python（标准库，用于模拟批量与同步成本对比的玩具程序）
**前置知识：** 第 17 阶段 · 第 14 课（提示词与语义缓存）
**预计时间：** 约 45 分钟

## 学习目标

- 说出三家提供商的批量 API（OpenAI、Anthropic、Google）及其通用的 50% 折扣与 24 小时交付保证。
- 计算在夜间分类工作负载上叠加“批量处理 + 缓存输入”的成本，并与同步未缓存基线进行对比。
- 将工作负载划分到交互式 / 半交互式 / 批量处理通道，并说明理由。
- 指出两个陷阱：部分交互性（用户期望快于 24 小时）和输出模式漂移（不同提供商的批量文件格式存在差异）。

## 问题所在

你的团队正在交付一个夜间报告生成流水线。包含 50,000 份文档，对每份文档进行摘要，对摘要进行聚类，并起草高管简报。以同步方式运行需要 4 小时，每晚成本为 2,000 美元。这时你听说了批量 API。

采用批量处理可获得 50% 的折扣。同时，你在系统提示词上启用提示词缓存（该提示词在所有 5 万次调用中共享）。两者叠加后，账单降至每晚 180 美元——仅为基线的约 9%。同样的流水线，仅需三项配置更改。

批量处理是 LLM 成本优化工具包中最便宜却最常被忽视的杠杆。主要原因在于组织架构层面：当 SLA 实际上只是“次日早晨前交付”时，团队却误以为是“实时”。本课旨在教你避免让 90% 的成本白白流失。

## 核心概念

### 三大批量 API

**OpenAI Batch API**：通过上传 JSONL 文件提交请求列表。承诺 24 小时内交付（实践中通常为 2-8 小时）。输入和输出 token 均享受 50% 折扣。端点为 `/v1/batches`。符合缓存条件的输入还可额外享受缓存输入定价。

**Anthropic Message Batches**：支持 JSONL 上传。24 小时交付周期。50% 折扣。支持 `cache_control`——缓存写入需显式触发，读取在批量处理过程中自动完成。

**Google Vertex AI Batch Prediction**：支持 BigQuery 或 GCS 作为输入源。Gemini 模型享有类似的 50% 折扣。可与 Vertex 流水线集成。

### 语义理解：异步，而非缓慢

批量处理的含义是“我承诺在 24 小时内返回结果”，而不是“这需要 24 小时”。典型的 P50（中位数）耗时为 2-6 小时。提供商会在 GPU 资源利用率较低的闲时窗口调度你的批量任务。

### 与缓存叠加使用

针对 5 万份文档进行摘要，且共用同一个 4K token 的系统提示词：

- 同步未缓存：按全价计算 50000 × ($input × 4000 + $output × 200)。
- 同步已缓存：首次写入后系统提示词被缓存；剩余的 49999 次调用可享受 10 倍便宜的输入价格。
- 批量已缓存：上述所有优势叠加，并对读写操作均享受 50% 折扣。

叠加效果：批量处理 + 缓存 ≈ 同步未缓存账单的 10%。任何夜间运行且拥有共享系统提示词的工作负载都应采用此方案。

### 工作负载分流

**交互式**——用户等待响应。首字延迟（TTFT）至关重要。使用带提示词缓存的同步调用。无法批量处理。

**半交互式**——用户提交任务，几分钟后回来查看结果。使用异步队列，若批量处理不可用则回退至同步。适用于中等规模的 RAG 索引构建。

**批量处理**——用户期望“次日早晨”或“一小时内”获取结果。内容流水线、大规模分类、离线分析。始终使用批量处理，并始终叠加缓存。

常见误区：因为流水线处于生产环境就将一切归类为交互式。生产环境并不等同于低延迟指标——SLA 才是决定因素。

### “部分交互性”陷阱

某些功能看似具有交互性，但实际上能容忍 5-10 分钟的延迟。例如：带有“刷新”按钮的夜间客户健康报告。用户点击刷新，等待 10 分钟完全可以接受。但团队仍将其作为同步功能交付。50 个并发刷新请求的成本，是使用批量处理并通过邮件发送结果的 10 倍。

需要问自己的问题是：“对于这个用户来说，24 小时意味着什么？”如果答案是“他们根本不会察觉”，那就直接走批量处理。

### “输出模式”陷阱

不同提供商的批量文件格式各不相同：

- OpenAI：JSONL 格式，每行一个请求。
- Anthropic：JSONL 格式，每行一条消息；响应格式内嵌。
- Vertex：BigQuery 表或带有 TFRecord 的 GCS 前缀。

试图编写跨提供商的“单一批量客户端”意味着必须为每个提供商编写适配代码。那些宣称支持多提供商批量的网关（如 Portkey、LiteLLM 的部分版本）本质上仍是对原始格式的薄封装。

### 需要牢记的关键数字

- 各提供商批量折扣：输入和输出统一打 5 折。
- 交付周期 SLA：承诺 24 小时，典型 P50 为 2-6 小时。
- 叠加批量处理 + 缓存输入：约为同步未缓存成本的 10%。
- 工作负载分流原则：若能接受 24 小时延迟，一律使用批量处理。

## 关键术语

| 术语 | 常见说法 | 实际含义 |
|------|----------|----------|
| Batch API | “异步折扣” | 24 小时交付周期，享 5 折优惠 |
| JSONL | “批量格式” | 每行一个 JSON 请求；OpenAI/Anthropic 标准格式 |
| Message Batches | “Anthropic 批量” | Anthropic 的批量 API 产品名称 |
| Batch prediction | “Vertex 批量” | Vertex AI 的批量 API 产品 |
| Turnaround SLA | “24 小时承诺” | 保证值而非典型值；典型值为 2-6 小时 |
| Workload triage | “交互性决策” | 交互式 / 半交互式 / 批量处理的路由决策 |
| Output schema | “响应格式” | 各提供商的 JSONL 布局；不具可移植性 |
| Stacked discount | “批量 + 缓存” | 两者同时适用时的账单约为未缓存同步费用的 10% |
