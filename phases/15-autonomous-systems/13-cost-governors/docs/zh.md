# 动作预算、迭代上限与成本治理器

> 一家中型电商代理在团队启用“订单追踪”技能后，其月度 LLM 成本从 1,200 美元飙升至 4,800 美元。这不是定价错误。而是该代理发现了一个新循环并持续在其中消耗资源。微软的 Agent Governance Toolkit（2026年4月2日）将针对此类问题的防御措施标准化：每次请求的 `max_tokens`、每项任务的令牌与美元预算、每日/每月上限、迭代上限、分层模型路由、提示词缓存、上下文窗口管理、昂贵操作前的人工审核（HITL）检查点、以及预算超支时的紧急切断开关。Anthropic 的 Claude Code Agent SDK 也提供了同名但命名不同的基础组件。资金消耗速率限制——例如“10分钟内支出超过50美元即切断访问”——比月度上限能更快地捕获异常循环。

**类型：** 学习
**语言：** Python（标准库，分层成本治理器模拟器）
**前置知识：** 第15阶段 · 第10课（权限模式），第15阶段 · 第12课（持久化执行）
**预计时间：** 约60分钟

## 问题所在

自主代理在每一步都会消耗真金白银。聊天机器人的糟糕输出只是一句坏回复；而代理的糟糕循环则是一张账单。业界对这种故障模式的正式术语是 `“Denial of Wallet”`——代理不断推理、不断调用工具、不断产生计费记录，且没有任何机制能阻止它，因为系统最初并未设计此类防护。

解决方案不是设置单一数值。而是一组在不同时间尺度和粒度上叠加的限制层：按次、按任务、按小时、按天、按月。设计良好的限制层能在几分钟内捕获失控循环，几小时内发现缓慢泄漏，一天内拦截劣质版本发布。当代理具有长周期和自主性时，同一套限制层也能确保预算始终受控。

这是一堂工程实践课：数学计算很简单，真正的难点在于团队的纪律性。下文列出的所有限制项名称均源自微软 Agent Governance Toolkit 或 Anthropic Claude Code Agent SDK 的文档。

## 核心概念

### 成本治理器栈

1. **单次请求的 `max_tokens`。** 简单直接。防止任何单次调用生成无限制的响应内容。
2. **按任务令牌预算。** 在整个运行过程中，总令牌数不得超过 N。达到上限时硬性停止。
3. **按任务美元预算。** 与令牌预算逻辑相同，但以货币计量。在 Claude Code 中称为 `max_budget_usd`。
4. **按工具调用上限。** 每种工具（如 `WebFetch`、`shell_exec` 等）的调用次数不得超过 N。
5. **迭代上限（`max_turns`）。** 代理主循环的总迭代次数；防止无限推理循环。
6. **按分钟/小时/天/月上限。** 滑动时间窗口。在不同时间尺度上捕获资源泄漏。
7. **资金消耗速率限制。** 例如，“若10分钟内支出超过50美元，则切断访问”。能在月度上限触发前快速拦截基于循环的资源消耗。
8. **分层模型路由。** 默认使用较小模型；仅当分类器判断任务复杂度需要时，才升级至更大模型。
9. **提示词缓存。** 系统提示词与稳定上下文存储在提供商缓存中；重新发送的令牌成本接近零。
10. **上下文窗口管理。** 通过压缩/摘要保持活跃上下文低于阈值；直接降低令牌成本。
11. **昂贵操作前的人工审核（HITL）检查点。** 在执行已知昂贵的操作（长时间工具调用、大文件下载、高成本模型升级）前，需人工确认。
12. **预算超支紧急切断开关。** 任何一项上限被触发时立即中止会话。上限状态会被记录，需通过独立流程重新启用。

### 为什么采用限制层而非单一上限

单一月度上限只能在钱包耗尽后才捕获失控代理。单一按次上限在会话层面毫无作用。不同的故障模式需要不同时间尺度的监控：

- **失控循环**（代理卡在5秒重试中）：由速率限制捕获。
- **缓慢泄漏**（代理每任务执行约2倍预期工作量）：由每日上限捕获。
- **劣质版本发布**（新版本消耗5倍令牌）：由每周/月度上限捕获。
- **正常流量激增**（真实需求，非程序缺陷）：由每小时/每日上限配合清晰日志捕获。

### Claude Code 的预算控制面

Claude Code Agent SDK 公开了以下配置（参考官方文档）：

- `max_turns` —— 迭代上限。
- `max_budget_usd` —— 美元预算上限；超支时中止会话。
- `allowed_tools` / `disallowed_tools` —— 工具白名单与黑名单。
- 工具调用前的钩子（Hook）点，用于自定义成本核算。

结合权限模式阶梯（第10课）。一个未配置 `max_budget_usd` 的 `autoMode` 会话等同于缺乏治理的自主运行。Anthropic 明确指出自动模式必须配备预算控制；分类器功能与成本控制正交（相互独立）。

### 欧盟《人工智能法案》与 OWASP 智能体十大风险

微软的 Agent Governance Toolkit 覆盖了 OWASP Agentic Top 10 及欧盟《人工智能法案》第14条（人类监督）的要求。在欧盟地区进行生产部署时，日志记录与上限强制执行并非可选项。

### 实际观测案例：$1,200 → $4,800

微软文档中的真实案例：某电商代理在新增一个工具后，月度成本翻了三倍。该工具允许代理在每个会话中轮询订单状态。系统中既无循环检测机制，也无按工具调用的上限，更无周环比增长告警。最终修复方案是增加按工具调用上限以及每日增长告警。这是一个通用模板：每一个新暴露的工具接口都是一个潜在的循环入口；每个新工具都必须配备独立的上限与独立的告警机制。

## 动手实践

`code/main.py` 模拟了代理在有无分层成本治理器栈两种情况下的运行表现。模拟代理在若干步之后会陷入轮询循环；分层治理栈能在速率限制窗口内将其捕获，而单一月度上限则要等到几天后才会触发。

## 练习

1. 运行 `code/main.py`。确认在轮询循环轨迹下，速率限制是否在迭代上限之前触发。接着禁用速率限制，测量迭代上限捕获代理前它“花费”了多少资源。
2. 为浏览器代理（第11课）设计一套按工具调用的上限策略。哪个工具需要最严格的限制？哪个工具可以无限制运行而不产生风险？
3. 阅读微软 Agent Governance Toolkit 文档。列出该工具箱定义的所有上限类型。将每种上限映射到对应的故障模式（失控循环、缓慢泄漏、劣质版本发布、流量激增）。
4. 为一个实际任务（例如“处理仓库中的50个Issue”）估算整夜无人值守运行的成本。将 `max_budget_usd` 设置为点估计值的2倍。说明设置2倍余量的理由。
5. Claude Code 的 `max_budget_usd` 基于会话累计成本触发。请设计一个你打算在外部强制执行的互补型速率限制。什么条件会触发切断？重新启用又该如何操作？

## 关键术语

| 术语 | 常见说法 | 实际含义 |
|---|---|---|
| Denial of Wallet | “失控账单” | 代理循环持续产生费用，且无任何上限机制予以制止 |
| max_tokens | “按次上限” | 单次补全（completion）的令牌数量天花板 |
| max_turns | “迭代上限” | 单个会话中代理主循环的最大迭代次数 |
| max_budget_usd | “美元紧急切断开关” | 会话总成本上限；超支时立即中止 |
| Velocity limit | “速率上限” | 短时间窗口内的支出限制（例如：10分钟内不超过50美元） |
| Tiered routing | “小模型优先” | 默认使用低成本模型；仅当分类器判定需要时才升级 |
| Prompt caching | “缓存的系统提示词” | 提供商侧缓存使重复发送的令牌成本趋近于零 |
| HITL checkpoint | “人工审批关卡” | 执行昂贵操作前必须经过人工确认 |
