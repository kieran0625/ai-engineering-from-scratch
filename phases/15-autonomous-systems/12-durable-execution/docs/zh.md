# 长期运行的后台代理：持久化执行

> 生产环境中的长周期代理并不运行在 `while True` 中。每次 LLM 调用都会变成一个带有检查点、重试和重放机制的 Activity。Temporal 的 OpenAI Agents SDK 集成于 2026 年 3 月正式 GA。Claude Code Routines（Anthropic）在无持久化本地进程的情况下运行计划内的 Claude Code 调用。会话在需要人工输入时暂停，能够抵御部署重启，并通过 `thread_id` 作为键从最新的检查点恢复。在这些新的人机交互设计背后，是一个老模式——工作流编排——只是多了一个新变量：将 LLM 调用视为非确定性活动，并在恢复时必须进行确定性重放。

**类型：** 学习
**语言：** Python（标准库，极简持久化执行状态机）
**前置知识：** 第 15 阶段 · 10（权限模式），第 15 阶段 · 01（长周期代理）
**耗时：** 约 60 分钟

## 问题所在

考虑一个运行四小时的代理。它调用了三个工具，向用户提示了两次，并进行了四十次 LLM 调用。运行到一半时，其宿主机重启了。会发生什么？

- 在朴素的 `while True` 循环中：一切丢失。运行从头重新开始。三次工具调用（带有真实副作用）会再次执行。用户会被再次提示已批准的事项。四十次 LLM 调用会被重新计费。
- 使用持久化执行：运行会从最近的检查点恢复。已完成的活动不会重新执行；它们的结果会从持久化日志中重放。用户无需重新批准已批准的事项。已进行的 LLM 调用不会被重新计费。

这与工作流引擎过去十年提供的模式相同（Temporal、Cadence、Uber 的 Cherami）。新的变化在于，LLM 调用现在被视为一种活动——非确定性、高成本、具有副作用——并且能完美契合此模式。

本课的核心主题：长周期可靠性会衰减（METR 观察到“35 分钟退化”现象——成功率随周期长度大致呈二次方下降）。持久化执行使得运行时间可以超过可靠性曲线所支持的范围。如果设计得当，这是一种安全失败的新方式；如果设计不当，则会导致不安全地失败。

## 核心概念

### 活动、工作流与重放

- **工作流（Workflow）**：确定性编排代码。定义活动的序列、分支和等待逻辑。必须是确定性的，以便能够从事件日志中重放而不会产生意外的分歧。
- **活动（Activity）**：非确定性且可能失败的工作单元。包括 LLM 调用、工具调用、文件写入、HTTP 请求等。每个活动都会记录其输入和（完成后的）输出。
- **事件日志（Event log）**：持久化存储后端。记录每一次活动的开始、完成、失败、重试以及每一个工作流决策。
- **重放（Replay）**：在恢复时，工作流代码从头重新运行；所有已完成的活动直接返回其记录的结果而不重新执行。只有未完成的活动才会真正被执行。

这与 React 针对虚拟 DOM 进行重渲染，或 Git 从提交记录重建工作树的结构相同。编排器的确定性正是让持久化变得低成本的原因。

### 为什么 LLM 调用契合该模式

LLM 调用具备以下特征：
- 非确定性（temperature > 0；即使 temperature 为 0，跨模型版本也会产生漂移）。
- 高成本（涉及金钱和延迟）。
- 可能失败（受限于速率限制、超时等）。
- 具有副作用（如果调用了外部工具）。

这完全符合活动的特征画像。将每次 LLM 调用封装为活动，即可实现带指数退避的重试、跨重启的检查点保存，以及用于调试的可重放追踪记录。

### 以 `thread_id` 为键的检查点

LangGraph、Microsoft Agent Framework、Cloudflare Durable Objects 和 Claude Code Routines 均收敛于相同的 API 形态：通过 `thread_id`（或等效标识符）来识别会话；每次状态转换都会持久化到后端（默认 PostgreSQL，开发环境用 SQLite，缓存用 Redis）；恢复时读取最新的检查点。

后端选择至关重要：

- **PostgreSQL**：持久化强、可查询、能抵御部署中断。LangGraph 的默认选项。
- **SQLite**：仅限本地开发；跨主机时会丢失数据。
- **Redis**：速度快但易失，除非配置了 AOF 或快照。
- **Cloudflare Durable Objects**：透明分布式；由唯一键限定作用域；可维持数小时至数周。

### 将人工输入作为一等公民的状态

“先提议后提交”（第 15 课）需要一个持久的“等待人工”状态。工作流在此暂停，外部队列持有待处理请求，审批通过后恰好从该点恢复。没有持久化能力时这只是尽力而为；有了持久化，夜间收到的审批会在次日早晨无缝接续工作流。

### 35 分钟退化现象

METR 观察到，所有被测的代理类别在连续运行约 35 分钟后均会出现可靠性衰减。任务时长翻倍，故障率大致翻四倍。持久化执行并不能解决此问题；它只是让你能够突破可靠性曲线所支持的时间上限。安全的做法是将持久化与“重新进入时需新鲜 HITL”的检查点策略相结合，并配合预算熔断开关（第 13 课）以固定总计算量，不受墙钟时间影响。

### 何时不应使用持久化执行

- 运行时间短于几分钟且无人工输入的代理。开销大于收益。
- 严格只读的检索任务。
- 正确性要求在一个上下文窗口内端到端完成的任务（部分推理任务；部分一次性生成任务）。

## 实践应用

`code/main.py` 使用 Python 标准库实现了一个极简的持久化执行引擎。它支持：

- `@activity` 装饰器，将输入和输出记录到 JSON 事件日志中。
- 用于编排活动序列的工作流函数。
- `run_or_replay(workflow, event_log)` 函数，在不重新执行的情况下重放已完成的活动。

驱动程序模拟了一个包含三个活动的工作流，在运行中途崩溃，并展示了（a）朴素重试会重新执行所有内容，与（b）重放仅运行缺失活动的对比。

## 交付部署

`outputs/skill-durable-execution-review.md` 用于审查拟议的长期代理部署是否符合正确的持久化执行架构：包括活动划分、确定性保证、检查点后端、人工输入状态管理以及恢复时的 HITL 策略。

## 练习

1. 运行 `code/main.py`。观察朴素重试与重放之间在活动执行次数上的差异。更改崩溃点，并展示重放计数随之相应变化。

2. 将玩具引擎改造为显式使用 `thread_id`。模拟两个共享该引擎的并发会话，并确认它们的事件日志不会发生冲突。

3. 选取玩具引擎中的一个活动。引入一个非确定性因素（例如在工作流决策内部使用墙钟时间戳）。演示重放时产生的分歧。解释真实引擎如何处理此类情况（副作用注册、`Workflow.now()` API）。

4. 阅读 LangChain 的文章《Production deep agents 背后的运行时》。列出运行时持久化的所有状态，并说明每种状态覆盖了哪种故障模式。

5. 为一个 6 小时的自主编码任务设计检查点策略。你在哪些节点设置检查点？崩溃恢复的流程是怎样的？哪些环节需要新鲜的人工介入（HITL）？

## 关键术语

| 术语 | 人们常说的说法 | 实际含义 |
|---|---|---|
| Workflow（工作流） | “代理脚本” | 确定性编排代码；可从事件日志重放 |
| Activity（活动） | “一个步骤” | 非确定性单元（LLM 调用、工具调用）；前后均有日志记录 |
| Event log（事件日志） | “底层存储” | 每次状态转换的持久化记录 |
| Replay（重放） | “恢复” | 重新运行工作流；已完成的活动直接返回记录结果，不重新执行 |
| Checkpoint（检查点） | “存档点” | 以 thread_id 为键的持久化状态；恢复时采用最新覆盖原则 |
| thread_id | “会话键” | 限定持久化状态作用域的标识符 |
| 35-minute degradation（35 分钟退化） | “可靠性衰减” | METR 观测：成功率随运行周期大致呈二次方下降 |
| Non-determinism（非确定性） | “重放漂移” | 墙钟时间、随机数、LLM 输出；必须注册为副作用 |
