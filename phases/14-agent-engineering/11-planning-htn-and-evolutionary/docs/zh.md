# 基于 HTN 与进化搜索的规划

> 符号规划适用于能够证明计划正确性的场景。进化代码搜索适用于适应度函数可由机器验证的场景。ChatHTN（2025）和 AlphaEvolve（2025）展示了它们在与 LLM 结合时各自能解锁的能力。

**类型：** 构建
**语言：** Python (标准库)
**前置知识：** 第 14 阶段 · 02（ReWOO 与 Plan-and-Execute）
**耗时：** 约 75 分钟

## 学习目标

- 解释层次任务网络（HTN）：任务、方法、算子、前置条件、效果。
- 描述 ChatHTN 的混合循环——符号搜索配合 LLM 回退分解。
- 解释 AlphaEvolve 的进化循环，以及为何它仅适用于编程式评估器。
- 在标准库中实现一个简易 HTN 规划器及一个简易进化搜索算法。

## 问题背景

ReWOO（课程 02）、Plan-and-Execute 和 ReAct 涵盖了大多数智能体规划场景。但以下两类情况它们处理得不够好：

1. **具有可证明正确性的计划。** 调度、航线规划、合规工作流——计划必须在构造上就是正确的。偶尔会幻觉出某个步骤的流畅 LLM 计划是不可接受的。
2. **具备机器可检查适应度函数的优化。** 矩阵乘法、调度启发式算法、编译器优化通道——目标不是“一个正确的计划”，而是“最优的计划”。

HTN 规划与 AlphaEvolve 分别解决上述两个不同的问题。两者都将 LLM 用作放大器，而非替代品。

## 核心概念

### 层次任务网络（HTN）

HTN 包含以下要素：

- **任务（Tasks）**——复合任务（需进一步分解）和基本任务（可直接执行）。
- **方法（Methods）**——将复合任务分解为子任务的方式，附带前置条件。
- **算子（Operators）**——带有前置条件和效果的基本动作。
- **状态（State）**——一组事实集合。

规划过程：给定目标任务和初始状态，寻找一种分解方案，将其转化为一系列基本算子，且这些算子的前置条件按顺序依次满足。

HTN 的历史早于 LLM，至今仍是可证明正确性计划的参考标准。

### ChatHTN（Gopalakrishnan 等，2025）

ChatHTN（arXiv:2505.11814）将符号 HTN 与 LLM 查询交错进行：

1. 尝试使用现有方法分解当前复合任务。
2. 若无适用方法，则向 LLM 提问：“在状态 `s` 下，你会如何分解 `task`？”
3. 将 LLM 的回复翻译为候选子任务。
4. 对照算子模式进行验证；拒绝无效的分解。
5. 递归执行。

论文的核心主张：生成的每个计划都是可证明正确的，因为 LLM 的建议仅作为候选分解进入系统，绝不会直接修改计划。符号层负责保证正确性；LLM 用于扩充方法库。

在线方法学习（OpenReview `gwYEDY9j2x`，2025 后续研究）引入了一种学习器，通过回归分析泛化 LLM 生成的分解结果——可将 LLM 查询频率降低高达 75%。

### AlphaEvolve（Novikov 等，2025）

AlphaEvolve（arXiv:2506.13131，DeepMind，2025 年 6 月）是另一种范式：由 Gemini 2.0 Flash/Pro 集成模型编排的进化代码搜索。

循环流程：

1. 以种子程序 + 编程式评估器（返回适应度分数）为起点。
2. LLM 集成模型提出变异方案。
3. 将变异后的代码传入评估器运行。
4. 保留最优解；再次进行变异。

已公布的成果：

- 56 年来首次在 4x4 复数矩阵乘法上超越 Strassen 算法（仅需 48 次标量乘法）。
- 通过 Borg 调度启发式算法，为 Google 节省了 0.7% 的计算资源。
- 在前沿工作负载上，使 FlashAttention 提速 32%。

硬性约束：适应度函数必须可由机器验证。对自然语言回答进行进化搜索无法收敛。

### 何时使用哪种方案

| 问题类别 | 推荐方案 | 原因 |
|---------------|-----|-----|
| 带硬约束的调度 | HTN + ChatHTN | 可证明的正确性 |
| 编译器优化 | AlphaEvolve | 机器可验证的适应度 |
| 多步任务执行 | ReAct / ReWOO | LLM 参与循环，无形式化保证 |
| 带测试的代码改进 | AlphaEvolve | 测试用例即评估器 |
| 策略约束的自动化 | HTN | 前置条件编码了业务策略 |

### 常见误区

- **缺少算子的 HTN。** 若没有前置条件/效果的模式定义，正确性声明将不攻自破。ChatHTN 的“LLM 建议分解”依赖模式来拒绝无效操作。
- **缺乏真实评估器的 AlphaEvolve。** “问 LLM 代码是否更好”不能算作适应度函数。评估器必须是确定性的且运行快速。
- **过度设计。** 大多数智能体任务都不需要这两种方案。应优先尝试 ReAct 或 ReWOO。

## 动手实现

`code/main.py` 实现了两个示例程序：

- 一个基于标准库的 HTN 规划器，包含算子、方法、前置条件、效果，以及当复合任务无匹配方法时触发的 `LLMFallback`。“LLM”被替换为脚本化的分解器，以便规划器离线运行。
- 一个针对算术程序的标准库进化搜索：生成表达式，使其输出在测试集上最小化 `|f(x) - target|`。评估器为确定性程序。

运行方式：

```
python3 code/main.py
```

运行日志将展示 HTN 规划器如何分解复合任务（包含中途触发 LLM 回退），以及进化循环如何收敛至目标表达式。

## 实际应用

- **HTN 规划器**——`pyhop`、`SHOP3`，或根据特定领域策略自行开发。
- **ChatHTN**——研究代码；该模式（符号规划 + LLM 回退）可无缝移植到任意 HTN 规划器。
- **AlphaEvolve**——DeepMind 论文；该模式（集成模型 + 评估器）具备可复现性。OpenEvolve 等类似开源分支正在涌现。
- **智能体框架**——目前尚无原生支持 HTN 或 AlphaEvolve 的框架。可将其作为子智能体或后台工作进程来实现。

## 部署实践

`outputs/skill-hybrid-planner.md` 生成一个混合规划器脚手架（HTN 或进化型），并明确界定 LLM 的作用范围。

## 练习

1. 为 HTN 规划器添加回溯功能：当算子的后置条件在运行时失败时，回滚状态并尝试下一个方法。
2. 为 ChatHTN 添加 LLM-方法缓存：当 LLM 在状态模式 `P` 下分解任务 `T` 时，保存结果。下次调用时优先检查方法库。
3. 将进化搜索的评估器替换为真实的测试套件。进化出一个能通过 20 个测试用例的排序函数；报告收敛所需的代数。
4. 阅读 AlphaEvolve 的评估器设计文档。为你关注的领域设计一个评估器（如 SQL 查询优化、测试套件最小化、部署 YAML 校验）。
5. 组合应用：使用 HTN 将复合任务分解为子任务，然后对每个子任务的基本算子使用进化搜索。它在哪些场景下表现优异？又在哪些场景下属于过度设计？

## 关键术语

| 术语 | 常见说法 | 实际含义 |
|------|----------------|------------------------|
| HTN | “层次规划器” | 带有算子、前置条件和效果的任务分解 |
| 方法 | “分解规则” | 将复合任务拆分为子任务的方式 |
| 算子 | “基本动作” | 带有前置条件和效果的具体步骤 |
| ChatHTN | “LLM + HTN” | 符号规划器在无匹配方法时向 LLM 求助 |
| AlphaEvolve | “进化代码搜索” | 集成 LLM 对代码进行变异；确定性评估器进行选择 |
| 适应度函数 | “评估器” | 针对输出的确定性、机器可验证评分 |
| 在线方法学习 | “缓存的 LLM 分解” | 存储并泛化 LLM 计划以降低查询成本 |
