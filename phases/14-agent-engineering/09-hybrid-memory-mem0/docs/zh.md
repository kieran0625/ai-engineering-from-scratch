# 混合记忆：向量 + 图 + KV（Mem0）

> Mem0（Chhikara 等，2025）将记忆视为三个并行存储——向量用于语义相似度匹配，KV 用于快速事实查找，图用于实体关系推理。在检索时，一个评分层会将这三者融合。这是 2026 年外部记忆的工业级标准。

**类型：** 构建
**语言：** Python（stdlib）
**前置条件：** 第 14 阶段 · 07（MemGPT），第 14 阶段 · 08（Letta Blocks）
**耗时：** 约 75 分钟

## 学习目标

- 解释为什么单一存储（仅向量、仅图或仅 KV）不足以支撑 Agent 记忆。
- 说出 Mem0 的三个并行存储及其各自优化的目标。
- 描述 Mem0 的融合评分机制（相关性、重要性、时效性），并解释为何它是加权求和而非层级结构。
- 使用标准库实现一个玩具级的三存储记忆系统，包含一个向所有存储写入数据的 `add()` 和一个用于融合结果的 `search()`。

## 问题所在

单一存储无法同时满足三类查询需求：

- **语义相似度** —— “我们上周讨论过关于 Agent 漂移的什么内容？” 向量存储胜出；KV 和图存储会遗漏。
- **事实查找** —— “用户的电话号码是多少？” KV 存储胜出；向量存储效率低下，图存储则大材小用。
- **关系推理** —— “哪些客户共享同一个计费主体？” 图存储胜出；向量和 KV 存储无法回答。

生产环境的 Agent 在一次会话中会同时发起这三类查询。单一存储的记忆系统必然在其中两类上出错。Mem0 的贡献在于通过一个评分函数将三者融合，并在统一的 `add`/`search` 接口表面之下将它们串联起来。

## 核心概念

### 三个并行存储

Mem0（arXiv:2504.19413，2025 年 4 月）在 `add(text, user_id, metadata)` 上的流程：

1. 从文本中提取候选事实（由 LLM 驱动的步骤）。
2. 将每个事实写入向量存储（生成嵌入向量）以进行语义搜索。
3. 将每个事实写入 KV 存储，键为 `(user_id, fact_type, entity)` 以实现 O(1) 查找。
4. 将每个事实作为带类型的边写入图存储（Mem0g）以支持关系查询。

在 `search(query, user_id)` 上的流程：

1. 向量存储返回基于嵌入余弦相似度的 Top-K 结果。
2. KV 存储返回基于查询派生的 `(user_id, type, entity)` 键的直接命中结果。
3. 图存储返回从查询实体可达的子图。
4. 评分层将这三者融合。

### 融合评分

```
score = w_relevance * relevance(q, record)
      + w_importance * importance(record)
      + w_recency * recency(record)
```

- **相关性** —— 向量余弦相似度、KV 精确匹配、图路径权重。
- **重要性** —— 在写入时打标签或通过学习获得（某些事实更重要：如姓名、ID、策略）。
- **时效性** —— 自上次写入或读取以来的时间呈指数衰减。

权重会根据具体产品进行调优。聊天型 Agent 赋予更高的 `w_recency`；合规型 Agent 赋予更高的 `w_importance`；检索型 Agent 赋予更高的 `w_relevance`。

### Mem0g 与时间推理

Mem0g 增加了冲突检测器。当新事实与现有边冲突时，现有边会被标记为无效但不会被删除。时间查询（例如“用户三月份的城市是哪个？”）会遍历该时间点有效的子图。

这正是 Letta 的失效模式所泛化的合规级行为。

### 基准测试数据

Mem0 论文报告的数据（2025 年）：

- **LoCoMo**（长对话记忆）：91.6
- **LongMemEval**（长周期情景记忆）：93.4
- **BEAM 1M**（100 万 Token 记忆基准）：64.1

对比基线（完整上下文 128k LLM、扁平向量存储、扁平 KV）均落后 10 分以上。仅凭基准测试不足以证明选型合理性——实际运行形态才是关键——但这些数字表明，融合设计并非凑数的边缘方案。

### 作用域分类

Mem0 按作用域划分记忆：

- **用户记忆** —— 跨会话持久化，基于 `user_id` 索引。
- **会话记忆** —— 在单个线程内持久化。
- **Agent 记忆** —— 每个 Agent 实例的状态。

每次写入都需指定一个作用域。检索时可以跨作用域查询，并为每个作用域分配权重。不加思考地混合作用域是导致“助手把 Bob 的项目透露给 Alice”这类事故的原因。

### 该模式的常见陷阱

- **嵌入漂移**。向量结果在前一百次查询中表现良好，但随着语料库增长会逐渐退化。应定期重新嵌入高频使用的 Top-N 记录。
- **KV 模式蔓延**。`(user_id, type, entity)` 看起来很简单，直到每个团队都加入自己的 `type`。建议每季度审计一次类型集合。
- **图爆炸**。一个噪声提取器每条消息可能添加 50 条边。限制每次 `add` 调用的图写入数量；丢弃低置信度的边。

## 动手构建

`code/main.py` 在标准库中实现了三存储模式：

- `VectorStore` —— 使用简单的词元重叠相似度作为嵌入替代方案。
- `KVStore` —— 基于 `(user_id, fact_type, entity)` 键控的字典。
- `GraphStore` —— 带类型的边（主体、关系、客体、有效性）。
- `Mem0` —— 顶层外观类，包含 `add()`、`search()`、融合评分以及作用域感知的检索。
- 针对多用户、多会话对话的逐步执行追踪示例。

运行方式：

```
python3 code/main.py
```

输出结果展示了三条独立的召回路径以及融合后的 Top-K 结果。修改 `main()` 顶部的评分权重，即可观察排名的变化。

## 实际应用

- **Mem0（Apache 2.0）** —— 已具备生产就绪能力。可使用 Postgres + Qdrant + Neo4j 自行托管，或使用托管云服务。
- **Letta** —— 采用核心/召回/归档三层架构；支持接入自定义的向量和图后端。
- **Zep** —— 提供商业替代方案，内置时间知识图谱与事实提取功能。
- **自定义构建** —— 当你需要精确控制提取器（合规场景）或融合权重（时效性主导的语音 Agent）时使用。

## 练习

1. 将玩具级的向量相似度替换为真实的嵌入模型（如 sentence-transformers、Ollama、OpenAI embeddings）。在合成长对话上测量 recall@10。经过 1000 次写入后，排名是否会发生漂移？
2. 添加时间查询：`search(query, as_of=timestamp)`。仅返回在该时间点或之前有效的记录。哪个存储模块最需要改造？
3. 实现冲突检测器：如果传入的事实与图边冲突，则使旧边失效并记录两者。在“用户住在柏林” -> “用户住在里斯本”的场景下测试。
4. 将融合评分器扩展以包含 `user_feedback` 维度（对检索到的记录点赞）。如何防止刷分行为（即 Agent 只返回它已经喜欢的记录）？
5. 阅读 Mem0 文档（`docs.mem0.ai`）。将玩具代码移植到 `mem0` 客户端调用。在同一组 20 个测试查询上比较检索质量。

## 核心术语

| 术语 | 常见说法 | 实际含义 |
|------|----------|----------|
| 混合记忆 | “向量加图加 KV” | 三个存储并行写入，检索时融合 |
| 事实提取 | “记忆摄入” | LLM 步骤，将文本拆分为（实体、关系、事实）元组 |
| 融合评分 | “相关性排序” | 相关性、重要性、时效性的加权求和 |
| 作用域 | “记忆命名空间” | user / session / agent —— 决定谁能看到什么 |
| Mem0g | “记忆图” | 带有时间有效性的带类型边，用于关系查询 |
| 时间失效 | “软删除” | 标记冲突边为无效；绝不物理删除 |
| 嵌入漂移 | “检索腐烂” | 向量质量随语料库增长而下降；需定期重新嵌入 |
