# 工具使用与函数调用

> Toolformer（Schick 等，2023）开启了自监督工具标注。Berkeley Function Calling Leaderboard V4（Patil 等，2025）设定了 2026 年的标准：40% 智能体任务、30% 多轮对话、10% 真实提示词、10% 合成数据、10% 幻觉检测。单轮调用已解决。记忆、动态决策和长程工具链仍未解决。

**类型：** 构建
**语言：** Python（标准库）
**前置知识：** 第 14 阶段 · 01（智能体循环），第 13 阶段 · 01（函数调用深入解析）
**耗时：** 约 60 分钟

## 学习目标

- 解释 Toolformer 的自监督训练信号：仅在执行结果能降低下一个 token 损失时，才保留工具标注。
- 列出 BFCL V4 的五个评估类别及其各自衡量的内容。
- 实现一个基于标准库的工具注册表，包含 Schema 验证、参数强制转换和执行沙箱隔离。
- 诊断 2026 年的三大开放问题：长程工具链、动态决策和记忆机制。

## 问题背景

早期的工具使用关注的是：模型能否预测出正确的函数调用？现代的工具使用关注的是：模型能否在具备记忆、部分可观测性、从工具失败中恢复的情况下，跨 40 个步骤连续调用工具，且不幻觉出不存在的工具？

Toolformer 确立了基线：模型可以通过自监督学习掌握何时调用工具。BFCL V4 定义了 2026 年的评估目标。两者之间的差距，正是生产级智能体所处的实际空间。

## 核心概念

### Toolformer（Schick 等，NeurIPS 2023）

核心思想：让模型在其自身的预训练语料库中标注候选 API 调用。对每个候选调用执行操作。仅当包含工具结果能降低下一个 token 的损失时，才保留该标注。在过滤后的语料库上进行微调。

涵盖的工具：计算器、问答系统、搜索引擎、翻译器、日历。自监督信号纯粹关注工具是否有助于文本预测——无需人工标注。

规模效应：工具使用能力在大规模下涌现。小模型会因工具标注而受损；大模型则从中受益。这就是为什么 2026 年的前沿模型内置了强大的工具使用能力，而大多数 7B 模型仍需显式的工具使用微调才能保持可靠。

### Berkeley Function Calling Leaderboard V4（Patil 等，ICML 2025）

BFCL 是 2026 年事实上的评估标准。V4 构成如下：

- **智能体任务 (40%)** ——完整的智能体轨迹：包含记忆、多轮交互、动态决策。
- **多轮对话 (30%)** ——带有工具链的交互式对话。
- **真实提示词 (10%)** ——用户提交的真实提示词（更难的数据分布）。
- **合成数据 (10%)** ——合成测试用例。
- **幻觉检测 (10%)** ——检测何时不应调用任何工具。

V3 引入了基于状态的评估：在工具序列执行后，检查 API 的实际状态（例如“文件是否已创建？”），而不是匹配工具调用的 AST。V4 增加了网页搜索、记忆和格式敏感性类别。

2026 年的关键发现：单轮函数调用已基本解决。失败主要集中在记忆（跨轮次携带上下文）、动态决策（根据先前结果选择工具）、长程工具链（20 步以上出现漂移）以及幻觉检测（在没有合适工具时拒绝调用）。

### 工具 Schema

每个提供商都有各自的 Schema。它们在细节上有所不同，但结构一致：

```
name: string
description: string (what it does, when to use it)
input_schema: JSON Schema (properties, required, types, enums)
```

Anthropic 直接使用 `input_schema`。OpenAI 使用 `function.parameters`。两者均接受 JSON Schema。描述信息至关重要——模型依赖它们来选择正确的工具。糟糕的工具描述是导致选错工具的首要根本原因。

### 参数验证

绝不盲目信任工具调用。需进行以下验证：

1. **类型强制转换。** 模型可能返回字符串 `"5"`，而 Schema 要求为 `int`。若明确无误则进行强制转换；否则拒绝。
2. **枚举验证。** 如果 Schema 规定为 `status in {"open", "closed"}` 而模型输出了 `"in_progress"`，则拒绝并返回描述性错误。
3. **必填字段。** 缺少必填字段 -> 立即向模型返回错误观察结果，而非直接崩溃。
4. **格式验证。** 日期、邮箱、URL —— 使用具体的解析器进行验证，而非正则表达式。

每次验证失败都应返回结构化的观察结果，以便模型能够以正确的格式重试。

### 并行工具调用

现代提供商支持在一次助手回复中并行调用多个工具。流程如下：

1. 模型发出 3 个具有不同 `tool_use_id` 的工具调用。
2. 运行时执行这些调用（若相互独立则并行执行）。
3. 每个结果作为 `tool_result` 块返回，并通过 `tool_use_id` 进行关联。

工程准则：将关联 ID 视为关键要素。若交换它们，会导致工具与结果的错误路由。

### 沙箱隔离

工具执行构成了沙箱边界。详见第 09 课。简而言之：每个工具都应明确指定读写范围、网络访问权限、超时时间和内存上限。通用的 `run_shell(cmd)` 是危险信号；具体的 `git_status()` 更安全。

## 实际应用

每个提供商都有各自的工具 Schema——Anthropic、OpenAI、Gemini、Bedrock。如果需要支持多提供商，请使用适配层（如 OpenAI Agents SDK、Vercel AI SDK、LangChain 工具适配器）。BFCL 是参考基准——如果工具使用是产品的核心功能，请在发布前针对你的智能体运行该基准测试。

## 部署上线

`outputs/skill-tool-registry.md` 为给定任务领域生成工具目录、Schema 和注册表。包含描述质量检查（每个工具的描述是否明确告知模型何时使用该工具？）。

## 练习

1. 添加一个“无操作”工具，允许模型明确拒绝使用任何其他工具。在类 BFCL 的幻觉测试中进行评估。
2. 实现针对“字符串型整数”和“字符串型浮点数”的参数强制转换。强制转换在何处开始掩盖真正的 Bug？
3. 添加每个工具的超时设置和熔断器（连续失败 3 次后拒绝该工具 60 秒）。这会如何改变模型的恢复机制？
4. 阅读 BFCL V4 的描述文档。选择一个类别（例如“多轮对话”），并将 10 个示例提示词输入你的智能体进行测试。报告通过率。
5. 将标准库验证器移植到 Pydantic 或 Zod。Pydantic/Zod 捕获到了哪些简易验证器遗漏的问题？

## 关键术语

| 术语 | 常见说法 | 实际含义 |
|------|----------|----------|
| Function calling | “工具使用” | 使用经过验证的 Schema 进行结构化输出的工具调用 |
| Toolformer | “自监督工具标注” | Schick 2023 —— 仅保留其结果能降低下一个 token 损失的工具调用 |
| BFCL | “伯克利函数调用排行榜” | 2026 基准测试：40% 智能体任务、30% 多轮对话、10% 真实提示词、10% 合成数据、10% 幻觉检测 |
| Tool schema | “面向模型的函数签名” | 名称、描述、参数的 JSON Schema |
| tool_use_id | “关联 ID” | 将工具调用与其结果绑定；对并行分发至关重要 |
| Hallucination detection | “知道何时不调用” | V4 类别：在没有合适工具时拒绝调用 |
| Argument coercion | “字符串转整型修复” | 针对可预测的 Schema 不匹配进行有限修正；若存在歧义则拒绝 |
| Sandboxing | “工具执行边界” | 每个工具的读写范围、网络权限、超时时间、内存上限 |
