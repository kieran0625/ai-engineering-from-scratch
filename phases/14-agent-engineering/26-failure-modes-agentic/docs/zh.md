# 失败模式：智能体为何会出错

> MASFT（伯克利，2025）将 14 种多智能体失败模式归类为 3 个类别。微软的《分类法》记录了现有 AI 失败模式在智能体环境中如何被放大。行业实地数据一致指向五种反复出现的模式：幻觉动作、范围蔓延、级联错误、上下文丢失、工具误用。

**类型：** 学习 + 构建
**语言：** Python（标准库）
**前置条件：** 第 14 阶段 · 05（自我优化与 CRITIC），第 14 阶段 · 24（可观测性）
**耗时：** 约 60 分钟

## 学习目标

- 说出 MASFT 的三个失败类别，以及每个类别中至少四种具体模式。
- 解释为何智能体失败会放大现有的 AI 失败模式（如偏见、幻觉）。
- 描述五种行业反复出现的模式及其缓解措施。
- 实现一个基于标准库的检测器，为智能体轨迹打上失败模式标签。

## 问题所在

团队发布的智能体在 90% 的轨迹上表现正常。那 10% 的失败并非随机噪声——它们集中在少数几个反复出现的类别中。一旦你能准确命名它们，就能对其进行监控并修复。

## 核心概念

### MASFT（伯克利，arXiv:2503.13657）

多智能体系统失败分类法。14 种失败模式被聚类为 3 个类别。标注者间 Cohen's Kappa 系数为 0.88——表明这些类别具有可靠的区分度。

核心观点：失败是多智能体系统中的根本性设计缺陷，而非仅靠改进基础模型就能解决的 LLM 局限性。

### 微软《智能体 AI 系统失败模式分类法》

- 现有的 AI 失败（偏见、幻觉、数据泄露）在智能体环境中会被放大。
- 新的失败源于自主性：大规模下的非预期行为、工具误用、目标漂移。
- 该白皮书是智能体产品的风险登记册。

### 《智能体 AI 故障特征分析》（arXiv:2603.06847）

- 失败源于编排逻辑、内部状态演化以及与环境的交互。
- 不仅仅是“代码写错了”或“模型输出了坏内容”。

### 《LLM 智能体幻觉综述》（arXiv:2509.18970）

两种主要表现形式：

1. **指令遵循偏差** —— 智能体未遵循系统提示词。
2. **长程上下文误用** —— 智能体遗忘或错误应用了早期轮次的上下文。

子意图错误：遗漏（漏掉步骤）、冗余（重复步骤）、混乱（步骤顺序错乱）。

### 五种行业反复出现的模式

Arize、Galileo、NimbleBrain 在 2024-2026 年的实地分析得出一致结论：

1. **幻觉动作**。智能体调用了不存在的工具，或捏造了参数。
2. **范围蔓延**。智能体将任务范围扩大到用户要求之外（例如创建多余的 PR、发送多余的邮件）。
3. **级联错误**。一次错误的调用引发下游连锁反应。一个虚构 SKU 的幻觉触发了四次 API 调用——演变为多系统事故。
4. **上下文丢失**。长周期任务遗忘了早期轮次的约束条件。
5. **工具误用**。使用正确的工具但传入了错误的参数，或直接调用了错误的工具。

级联错误是最致命的。智能体无法区分“我失败了”和“任务不可能完成”，经常在收到 400 错误时幻觉出一条成功消息以强行闭环。

### 缓解措施：每一步设置检查门控

在推理链的每一步设置自动化验证门控，对照环境状态检查事实依据。具体措施包括：

- 每步安全分类器（第 21 课）。
- 工具调用参数校验（第 06 课）。
- 将检索内容与已知事实交叉核对（第 05 课，CRITIC）。
- 通过重新探测状态来检测成功幻觉（文件是否真的被创建了？）。

### 失败监控的常见误区

- **仅标记崩溃**。大多数智能体失败会产生看似正常的输出。需要内容级别的检查。
- **缺乏基线**。漂移检测需要一个“最后已知良好状态”；没有它就无法判断“情况正在恶化”。
- **告警泛滥**。每次失败都会触发一次呼叫。需要进行聚类并限制频率。

## 动手构建

`code/main.py` 实现了一个基于标准库的失败模式打标签器：

- 覆盖这五种模式的合成轨迹数据集。
- 针对每种模式的检测函数（基于工具调用、输出、重复动作的特征模式）。
- 一个为每条轨迹打标签并报告模式分布的标签器。

运行方式：

```
python3 code/main.py
```

输出：逐条轨迹的标签 + 聚合分布，低成本复现 Phoenix 轨迹聚类所揭示的内容。

## 实际应用

- **Phoenix** 用于生产环境的漂移聚类（第 24 课）。
- **Langfuse** 用于会话回放与标注。
- **自定义** 用于你的可观测性平台无法检测的领域特定特征。

## 交付上线

`outputs/skill-failure-detector.md` 生成针对你所在领域定制的失败模式检测器，并接入轨迹存储库。

## 练习

1. 添加一个针对“成功幻觉”的检测器：智能体返回成功，但目标状态未发生变化。
2. 为你开发过的产品标记 100 条真实轨迹。哪种模式占主导？修复它的成本是多少？
3. 实现一个“级联半径”指标：给定第 N 步发生的失败，它影响了多少下游步骤？
4. 阅读 MASFT 的 14 种失败模式。挑选三种适用于你产品的模式，编写对应的检测器。
5. 将一个检测器接入 CI 流程：如果 >=5% 的轨迹标记了某种模式，则构建失败。

## 关键术语

| 术语 | 常见说法 | 实际含义 |
|------|----------------|------------------------|
| MASFT | “多智能体失败分类法” | 伯克利 14 种模式分类 |
| 级联错误 | “涟漪式失败” | 早期的一次失误沿 N 个步骤传播 |
| 上下文丢失 | “忘了约束条件” | 长周期轮次丢弃了早期轮次的事实 |
| 工具误用 | “用错工具/传错参数” | 调用合法但执行方式错误 |
| 成功幻觉 | “伪造完成” | 智能体在 400 错误时声称成功；状态未变 |
| 范围蔓延 | “越权/过度执行” | 智能体执行了超出要求的操作 |
| 指令遵循偏差 | “不服从” | 忽略系统提示词或用户约束 |
| 子意图错误 | “计划漏洞” | 计划执行中的遗漏、冗余、混乱 |
