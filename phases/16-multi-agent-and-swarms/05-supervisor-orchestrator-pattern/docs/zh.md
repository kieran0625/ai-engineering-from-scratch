# 主管/编排器-工作者模式

> 一个主导智能体负责规划与委派；专业的工作者在并行上下文中执行并汇报结果。这是 Anthropic Research 系统背后的模式（以 Claude Opus 4 作为主导，Sonnet 4 作为子智能体），在内部研究评估中比单智能体 Opus 4 提升了 90.2%。Anthropic 的工程博文指出，BrowseComp 上的性能差异有 80% 仅由 token 使用量就能解释——多智能体之所以胜出，很大程度上是因为每个子智能体都获得了全新的上下文窗口。本课程将从基础原语构建主管模式，并涵盖生产部署中的 2026 年工程经验教训。

**类型：** 学习 + 实践
**语言：** Python（标准库、`threading`）
**前置条件：** 第 16 阶段 · 04（基础模型）
**耗时：** 约 75 分钟

## 问题

研究是单智能体系统典型的失败任务。当你问“2023 年到 2026 年间多智能体系统发生了什么变化？”时，单个智能体会按顺序阅读五篇论文，用它们的文本填满一半的上下文，然后必须将它们放在一起进行推理。等到它读到第五篇时，已经忘记了第一篇的内容。它无法并行处理。

主管模式解决了这个问题：一个主导智能体规划搜索路径，将每个子问题委派给工作者，并进行综合。每个工作者都拥有独立的 20 万 token 窗口来回答一个狭窄的问题。主导智能体从不查看原始论文——只看工作者的摘要。

Anthropic 的生产环境 Research 系统在内部研究评估中相比单个 Opus 4 提升了 90.2%。同一篇博文指出，BrowseComp 的性能差异有 80% 仅由 *token 使用量* 就能解释。为每个子智能体提供全新的上下文是主要机制。

## 概念

### 模式

```
                 ┌──────────────┐
                 │   Lead       │  plans, decomposes,
                 │  (Opus 4)    │  synthesizes
                 └──┬────┬───┬──┘
                    │    │   │
            ┌───────┘    │   └───────┐
            ▼            ▼           ▼
      ┌─────────┐  ┌─────────┐  ┌─────────┐
      │ Worker1 │  │ Worker2 │  │ Worker3 │
      │(Sonnet) │  │(Sonnet) │  │(Sonnet) │
      └─────────┘  └─────────┘  └─────────┘
         fresh       fresh        fresh
         context     context      context
```

主导智能体从不阅读原始材料。在工作者完成工作之前，它们彼此看不到对方的输出。直到主导智能体进行综合。图中的每个箭头代表一次带有特定产物的交接。

### 为何胜出

三种机制：

1. **每个子智能体的全新上下文。** 探索“FIPA-ACL 传承”的工作者不会携带主导智能体规划时消耗的 4 万 token。它只为一个问题获得 20 万 token 的窗口。
2. **通过提示词实现专业化。** 主导智能体的提示词是“分解与综合”，而非“研究”。每个工作者的提示词都很具体：“找出 X 中发生的变化”。聚焦的提示词产生聚焦的输出。
3. **并行性。** 工作者并发运行。实际耗时（wall-clock time）约为 `max(worker_times) + plan + synthesis`，而非 `sum(worker_times)`。

### 工程经验（Anthropic 2025）

Anthropic 的博文列出了几项至今仍适用于 2026 年的生产经验：

- **根据查询复杂度调整投入规模。** 简单查询：一个智能体，3-10 次工具调用。复杂查询：10 个以上智能体。必须由主导智能体自行估算，而非调用方。
- **先广后深。** 先将问题分解为宽泛的子问题，如果答案需要深度，再为每个子问题生成更多工作者。
- **彩虹部署（Rainbow deployments）。** 智能体通常是长运行且有状态的。传统的蓝绿部署不适用。Anthropic 采用彩虹部署：在新版本逐步上线的同时，旧版本逐渐耗尽流量。
- **Token 用量占主导。** 多智能体的 token 消耗约为单智能体的 15 倍。仅在任务价值足以证明成本合理时才运行。

### LangGraph 的转变

LangGraph 最初发布了一个包含高级 `create_supervisor` 辅助函数的 `langgraph-supervisor` 库。2025 年，LangChain 将推荐方案改为直接通过工具调用来实现主管模式，因为工具调用能更好地控制 *主管能看到什么*（上下文工程）。该库仍然可用；但文档现在推荐使用工具调用形式。

### 失败模式

- **主导智能体幻觉出错误计划。** 如果主导智能体生成的子问题未能正确分解真实问题，工作者就会对错误的目标进行精确研究。
- **工作者过度探索。** 如果没有明确的范围边界，工作者会偏离被分配的子问题，从而污染综合步骤。
- **综合冲突。** 两个工作者返回了相互矛盾的事实。主导智能体必须重新提问（增加一轮）或明确记录分歧。暗中选择其中一方是最糟糕的失败：用户永远不会知道发生过分歧。

### 何时不该使用主管模式

- **顺序任务。** 如果步骤 2 确实需要步骤 1 的输出，并行性毫无用处。请使用流水线（CrewAI Sequential、LangGraph 线性图）。
- **简单查询。** 单智能体处理起来更快、更便宜。在生成工作者之前，应使用主导智能体的“调整投入规模”检查。
- **严格确定性。** 主管模式依赖 LLM 选择的委派。当审计/回放比适应性更重要时，静态图更好。

## 构建它

`code/main.py` 使用 `threading` 实现了包含三个并行工作者的主管模式。主导智能体将查询分解为子问题，工作者在每个子问题上并发运行，最后由主导智能体进行综合。这里没有真实的 LLM——工作者通过脚本模拟获取与摘要功能。

关键结构：

- `Lead.plan(query)` 将查询拆分为 3 个子问题。
- `Worker.run(sub_q)` 返回伪造的摘要（在生产环境中可以是任何使用工具的智能体）。
- `Lead.run(query)` 在线程中启动工作者，等待完成并综合结果。

运行：

```
python3 code/main.py
```

输出将显示计划、带有开始/结束时间戳的并行工作者追踪信息以及最终的综合结果。你可以看到实际耗时的优势：三个各需 0.3 秒的工作者总共只运行了约 0.35 秒，而不是 0.9 秒。

## 使用它

`outputs/skill-supervisor-designer.md` 接收用户查询并生成主管模式设计：主导智能体系统提示词、工作者角色、子问题分解规则以及综合模板。在构建新的研究型智能体系统前请使用此工具。

## 部署它

部署主管模式前的检查清单：

- **模型配对。** 主导智能体使用推理级模型（Opus 类、`o3` 类）。工作者使用更快、更便宜的模型（Sonnet、`o4-mini`）。
- **工作者超时。** 任何运行时间超过中位数 2 倍的工作者将被终止；主导智能体要么以更窄的范围重新生成，要么跳过它继续执行。
- **每个工作者的 Token 上限。** 设置硬性限制（例如预期综合输入量的 10 倍），防止失控的工作者耗尽预算。
- **可观测性。** 追踪主导智能体的计划、每个工作者的工具调用以及综合过程。这是事后调试的基础。
- **彩虹式上线。** 有状态的长运行智能体需要渐进式的版本过渡，而非热替换。

## 练习

1. 运行 `code/main.py`，然后将主导智能体修改为生成 5 个工作者而不是 3 个。观察实际耗时的影响。在此演示中，工作者数量达到多少时，生成开销会超过并行带来的节省？
2. 实现工作者超时机制：终止任何运行超过 0.5 秒的工作者，并由主导智能体综合剩余结果。你需要哪些可观测性数据才能知道某个工作者被截断了？
3. 为主导智能体的综合步骤添加冲突检测环节：如果两个工作者返回相互矛盾的答案，主导智能体应记录分歧而不是盲目选择其一。在不调用 LLM 的情况下，你如何检测矛盾？
4. 阅读 Anthropic 的 Research 系统工程博文。列出本玩具演示若要投入生产环境所需采用的三项实践。
5. 比较 LangGraph 的 `create_supervisor`（遗留版）与新的工具调用推荐方案。哪种方案能让你更好地控制主管能看到的内容？为什么 Anthropic 明确只传递子答案而不将原始工作者上下文传入综合步骤？

## 核心术语

| 术语 | 常见说法 | 实际含义 |
|------|----------|----------|
| Supervisor（主管） | “主导智能体” | 负责规划、委派和综合的编排智能体。本身不执行具体工作。 |
| Worker（工作者） | “子智能体” | 由主管调用的专注型智能体，具有狭窄的作用域和独立的上下文窗口。 |
| Orchestrator-worker（编排器-工作者） | “主管模式” | 同一概念的不同名称。2026 年的文献中两者混用。 |
| Fresh context（全新上下文） | “干净窗口” | 工作者的上下文从其系统提示词和被分配的问题开始，而非继承主导智能体的历史。 |
| Rainbow deployment（彩虹部署） | “渐进式上线” | 长运行且有状态的智能体需要带版本控制的逐步淘汰与替换，而非蓝绿部署。 |
| Token dominance（Token 主导） | “上下文是变量” | 据 Anthropic 所述，研究评估中 80% 的差异来自总 token 使用量，而非模型选择。 |
| Scale effort（调整投入规模） | “匹配智能体数量与复杂度” | 主导智能体评估查询难度，相应地生成 1 个或 10 个以上工作者。 |
| Synthesis conflict（综合冲突） | “工作者意见不一” | 两个工作者返回矛盾事实；主导智能体必须公开分歧，而非暗中选择其一。 |
