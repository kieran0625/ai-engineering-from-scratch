# 分层架构及其失效模式

> 分层结构本质上是监督者的嵌套。经理智能体管理子经理，子经理再管理执行层智能体。CrewAI `Process.hierarchical` 是教科书式的实现：`manager_llm` 负责动态委派任务并验证输出。LangGraph 的对应实现为 `create_supervisor(create_supervisor(...))`。当任务天然契合真实组织架构时，该模式最为自然。然而，它也是最容易退化为“管理层循环”的模式——经理智能体可能分配不当、曲解子级输出或无法达成共识。此时，顺序（Sequential）模式往往表现更好。

**类型：** 学习 + 构建
**语言：** Python (标准库)
**前置条件：** 第 16 阶段 · 05（监督者模式）
**耗时：** 约 60 分钟

## 问题

一旦掌握了监督者模式，很自然的下一步就是思考：“如果工人智能体本身也是监督者会怎样？”团队有子团队；公司有部门下的部门。分层架构正是对这种结构的映射。

核心问题在于：LLM 经理与人类经理并不相同。人类经理对其下属的知识储备有稳定的先验认知。而 LLM 经理会在每一轮推理中，仅根据当前上下文重新推演整个组织架构。上下文的微小漂移，就会导致整棵树的工作分配出现偏差。

## 概念

### 结构形态

```
                 Manager
                 ┌─────┐
                 └──┬──┘
           ┌────────┴────────┐
           ▼                 ▼
       Sub-Mgr A         Sub-Mgr B
       ┌─────┐           ┌─────┐
       └──┬──┘           └──┬──┘
         ┌┴──┬──┐          ┌┴──┐
         ▼   ▼  ▼          ▼   ▼
       W1  W2  W3         W4  W5
```

每个内部节点负责规划、委派和综合汇总。只有叶子节点才执行实际工作。

### 适用场景

- **组织架构映射清晰。** 如果任务本身具有明确的部门分工（例如“法务审核文档、财务审核文档、工程审核文档，最后向高管汇总”），分层结构非常直观。
- **局部汇总。** 每个子经理在向顶层经理汇报前，会先整合其团队的输出。顶层经理看到的是三个子经理的摘要，而非十五个工人智能体的原始输出。

### 失效场景

2026 年的复盘报告反复指出三种失效模式：

1. **任务分配错误。** 经理读取目标后，幻觉出一个分解方案，并将任务委派给了错误的子经理。由于子经理会忠实地处理接收到的内容，错误直到顶层综合汇总时才暴露出来——这比人类本可以拦截它的层级又高了一层。
2. **输出误读。** 子经理返回“无法验证主张 X”。顶层经理将其总结为“主张 X 未获确认”。语义在每一层传递中都会发生漂移。
3. **共识死循环。** 两个子经理意见不合；顶层经理要求它们协调；它们向下重新委派；工人智能体重跑；子经理返回略有差异的答案；循环往复。CrewAI 的 `Process.hierarchical` 通过步骤限制来防范此问题，但该限制本身现在变成了一个超参数。

### 决策关键

顺序模式（线性流水线）与分层模式：你的任务是否真的拥有独立的子团队，还是仅仅是一个伪装成分支树的线性流程？如果是后者，请使用顺序模式。如果是前者，请使用分层模式，但必须明确设定协调规则与预算。

### CrewAI 的实现方式

`Process.hierarchical` 将经理 LLM 部署在专业 Crew 之上。该经理：

- 接收顶层任务，
- 向各 Crew 分配子任务，
- 评估 Crew 的输出，
- 决定是接受结果、重新委派还是进行迭代。

文档：https://docs.crewai.com/en/introduction（在“核心概念”下查找“Hierarchical Process”）。

### LangGraph 的实现方式

LangGraph 使用嵌套的 `create_supervisor` 调用。内部监督者拥有自己的图结构；外部监督者将内部图视为一个不透明节点。这在调试上比 CrewAI 更清晰（你可以分别逐步执行每个图），但更难表达树结构的动态重塑。

参考：https://reference.langchain.com/python/langgraph-supervisor.

## 动手实践

`code/main.py` 运行一个三层分层架构：

- 顶层经理：将任务拆分为“工程”和“法务”分支，
- 工程子经理：进一步拆分为“前端”和“后端”工人智能体，
- 法务子经理：包含一个工人智能体。

演示环节对比了正常路径（各方达成一致）与**扰动路径**。在扰动路径中，顶层经理的错误分解将“法务”误标为“财务”，从而观察误差如何级联扩散——子经理忠实地执行财务工作，顶层综合器汇报财务结论，原始的法务问题则石沉大海。

运行：

```
python3 code/main.py
```

输出将并列展示两条路径，清晰对比“请求内容”与“交付结果”。

## 实际应用

`outputs/skill-hierarchy-fitness.md` 用于评估给定任务应采用分层模式、顺序模式还是扁平化监督者模式。输入：任务描述、组织架构、协调预算。输出：模式推荐及需要防范的具体失效模式。

## 生产部署建议

若在生产环境中采用分层架构：

- **将树深度限制在 2 以内。** 三层结构已经会让大部分错误脱离可观测范围。
- **明确协调预算。** 设定顶层经理必须做出最终决定的最大轮数。通常为 2 轮。
- **每次综合均需保留溯源信息。** 每个节点的摘要必须引用生成该摘要的叶子节点输出。
- **监控分解漂移。** 记录每一步经理的任务分解方案；并与用户原始查询进行比对。如果分解方案不再覆盖原始查询，立即触发告警。

## 练习

1. 运行 `code/main.py` 并对比正常路径与扰动路径。需要经过多少层经理交接，顶层输出才会完全偏离用户的原始问题？
2. 增加第三层（顶层 → 子层 → 孙层 → 工人）。测量随着深度增加，扰动路径自我修正的频率与完全偏离的频率之比。
3. 在每个子经理处实现一个“金丝雀”工人，始终向其询问未经修改的原始用户问题。利用金丝雀答案检测分解漂移。当金丝雀答案与综合答案不一致时，经理应作何反应？
4. 阅读 CrewAI 的 `Process.hierarchical` 文档。找出 CrewAI 应用的一个具体护栏机制（如步骤限制、manager_llm 约束），并说明它针对的是哪种失效模式。
5. 对比嵌套式 LangGraph 监督者与 CrewAI 的分层架构。哪一种更容易以较低成本检测到协调死循环？

## 核心术语

| 术语 | 常见说法 | 实际含义 |
|------|----------|----------|
| Hierarchical（分层） | “组织架构模式” | 监督者嵌套监督者；仅叶子节点执行工作。 |
| Manager LLM（经理大模型） | “老板” | 在内部节点负责分解、分配和验证的大语言模型。 |
| Decomposition drift（分解漂移） | “老板跑偏了” | 顶层经理的任务分解已不再覆盖原始问题。 |
| Reconciliation loop（协调死循环） | “无休止的会议” | 子经理意见不一；顶层重新委派；工人重跑；循环直至预算耗尽。 |
| Depth-2 ceiling（二层天花板） | “别超过两层” | 经验性护栏：3 层及以上会导致可观测性崩溃。 |
| Canary question（金丝雀问题） | “各层的基准真相” | 始终被询问原始查询且不作修改的工人，用于检测漂移。 |
| Provenance chain（溯源链） | “谁说了什么” | 从每次综合回溯至生成该结果的叶子节点输出。 |
