# 共享内存与黑板模式

> 2026 年的多智能体系统中并存着两种架构：**消息池**（所有智能体都能看到彼此的消息，如 AutoGen GroupChat 或 MetaGPT）和**带订阅的黑板**（智能体订阅相关事件，如 Context-Aware MCP 或 Matrix 框架）。它们都是多智能体系统中唯一具有状态的部分——这意味着有趣的 bug 都藏在这里。典型的故障模式是**记忆投毒**：一个智能体幻觉出一个“事实”，其他智能体将其视为已验证的信息，导致准确性逐渐衰减，其调试难度远高于直接崩溃。本课程将从标准库开始构建这两种结构，注入一次投毒攻击，并展示在生产环境中真正有效的三种缓解措施。

**类型：** 学习 + 构建
**语言：** Python (stdlib, `threading`)
**前置条件：** Phase 16 · 04 (Primitive Model), Phase 16 · 09 (Parallel Swarm Networks)
**时间：** ~75 分钟

## 问题

多智能体系统需要一个地方供智能体共享事实。一种字面意义上的选择是“在消息中传递一切”——但这只是用额外的复制操作重新发明了共享状态。另一种是“给每个人一个全局日志”——但全局日志会无限增长且极易被污染。第三种是“为每个智能体投射一个视图”——可扩展但模式设计繁重。

当一个智能体产生幻觉并将幻觉写入共享状态时，每个读取该状态的下游智能体都会将该幻觉当作事实接受。等到人类发现时，推理链已经深入五层，而根本原因是最初写入的第三条消息。调试多智能体的准确性衰减比调试程序崩溃更难。

这就是记忆投毒。它是 MAST 分类法中记录第二多的故障家族（Cemri et al., arXiv:2503.13657），且具有结构性特征：任何缺乏溯源信息和不可写验证器的共享内存设计，最终都会表现出此问题。

## 概念

### 两种主要拓扑

**全量消息池。** 每个智能体读取每条消息。AutoGen GroupChat 和 MetaGPT 使用此架构。简单、透明、可检查，但无法扩展到超过 ~10 个智能体，因为每个智能体的上下文会被其他智能体的工作填满。

```
agent-A ──write──▶ ┌────────────────┐ ◀──read── agent-D
                   │ message pool   │
agent-B ──write──▶ │                │ ◀──read── agent-E
                   │ (global log)   │
agent-C ──write──▶ └────────────────┘ ◀──read── agent-F
```

**带订阅的黑板。** 智能体声明对特定主题的兴趣；底层系统仅路由相关消息。CA-MCP (arXiv:2601.11595) 和 Matrix 去中心化框架 (arXiv:2511.21686) 使用此架构。扩展性更强，但需要预先进行模式设计以使订阅有意义。

```
                   ┌─ topic: prices ──┐
agent-A ──pub────▶ │                  │ ──▶ agent-D (subscribed)
                   ├─ topic: orders ──┤
agent-B ──pub────▶ │                  │ ──▶ agent-E (subscribed)
                   ├─ topic: alerts ──┤
agent-C ──pub────▶ │                  │ ──▶ agent-F (subscribed)
                   └──────────────────┘
```

### 何时哪种架构占优

- **全量消息池** 在智能体数量少 (< 10)、异构且对话周期短时占优。当所有人都能看到所有内容时，理清谁说了什么非常简单。
- **黑板** 在智能体数量多、角色同质但实例众多（群体智能）且对话长期运行时占优。路由可以节省 Token 成本并减少上下文污染。

生产系统通常混合使用：顶层使用小型全量消息池（规划层），下层使用黑板（执行层）。

### 记忆投毒的一个场景

三个智能体协作完成一项研究任务。Agent A 是检索智能体。Agent B 是摘要智能体。Agent C 是分析智能体。

1. A 抓取了一个页面并向共享状态写入一条消息：“该研究报告准确率提升了 42%。”
2. 实际抓取的页面说的是“提升 4.2%”。A 幻觉出了一个小数点位置错误。
3. B 读取共享状态后写入：“报告称准确率大幅提升 42%（来源：A）。”
4. C 读取共享状态后写入：“建议采纳——42% 的提升具有变革性。”
5. 最终报告引用了一个从未存在过的 42% 的数据。

没有智能体崩溃。没有测试失败。系统“正常运行”。幻觉通过共享状态从一个智能体的上下文渗透到了所有下游智能体的推理中。

### 为什么这是结构性问题

如果没有共享状态，智能体 A 的幻觉将局限于 A 的上下文中。下游智能体会重新抓取或重新推导，可能会发现错误。但在朴素的共享状态下，A 的上下文变成了所有人的上下文，幻觉被洗白成了事实。

问题不在于共享状态本身，而在于**缺乏溯源信息和独立验证器的共享状态**。三种缓解措施可解决此问题：

1. **为每次写入记录溯源信息。** 共享状态中的每条条目都记录写入者、时间戳、提示词以及（如果适用）智能体引用的来源。下游智能体会根据溯源信息保持审慎态度。
2. **版本化写入；将其视为仅追加。** 修正是一条覆盖旧条目的新条目，而非原地更新。审计轨迹得以保留。
3. **至少保留一个不能向共享状态写入的智能体。** 一个只读的验证器智能体会抽样检查条目、重新抓取来源并标记不一致之处。因为它不能向池中写入，所以不会被池子污染。

### 黑板的先例（Hayes-Roth, 1985）

黑板模式比 LLM 智能体早出现四十年。Hayes-Roth (1985, "A Blackboard Architecture for Control") 描述了观察全局黑板的专家“知识源”，它们贡献部分解决方案并触发其他源。2026 年的黑板（CA-MCP, Matrix）是同一模式，只是用 LLM 智能体作为知识源，用 JSON 块作为部分解决方案。旧文献中关于写入竞争、机会主义控制和一致性的解决方案已被现代系统重新发现。

### 投影 vs 全量视图

纯黑板给予每个订阅者相同的投影（按主题作用域）。更激进的设计是**每智能体投影**：每个智能体获得按其角色定制的视图。LangGraph 的状态归约器是 2026 年的标准实现——归约函数将全局状态折叠为特定角色的切片。

每智能体投影进一步扩展了规模，但需要模式支持。如果没有模式，你将在每个智能体的提示词中重建临时的投影逻辑。

### 写入竞争模式

多个智能体同时写入是一个并发问题，而不仅仅是 LLM 问题。三种模式有效：

- **顺序写入器（单生产者）。** 所有写入都通过一个协调员智能体序列化。简单，但是瓶颈。
- **带版本控制的乐观并发。** 每个条目都有版本号；写入者在版本不匹配时失败并重试。经典的数据库技术。
- **主题分区。** 不同智能体拥有不同的主题。无跨主题竞争。需要预先设计分区边界。

大多数 2026 年的框架默认使用顺序写入器，因为 LLM 调用足够慢，竞争很少发生，且瓶颈不会造成太大影响。

### 不可写验证器

最关键的缓解措施是只读验证器。实现规则如下：

- 验证器与团队共享状态（读取黑板或消息池）。
- 验证器没有共享状态的写入句柄——只有独立的验证通道。
- 验证器独立获取写入中引用的来源。标记分歧。
- 验证器的输出路由到人类或单独的决策智能体，绝不反馈回池中。

如果没有这种分离，验证器的输出将成为池中的新条目，这意味着被污染的池子会污染验证器，进而污染其验证结果。

## 构建它

`code/main.py` 在 stdlib Python 中实现了上述两种拓扑，并包含一个示例性投毒攻击及三种缓解措施。

- `MessagePool` —— 线程安全的仅追加日志，支持完整读取。
- `Blackboard` —— 基于主题键的发布/订阅，支持每智能体订阅。
- `ProvenanceEntry` —— 每次写入记录（writer, timestamp, prompt_hash, source_uri）。
- `PoisoningScenario` —— 运行一个三智能体研究任务，其中 Agent A 幻觉出小数点错误。打印最终报告。
- `Verifier` —— 一个只读智能体，负责重新抓取来源并标记不一致之处。在引入验证器的情况下运行相同场景。

运行：

```
python3 code/main.py
```

预期输出：
- 运行 1（无验证器）：幻觉出的 42% 传播到最终报告中。
- 运行 2（带验证器）：验证器标记出不一致，池子被标记为“flagged”，最终报告包含撤回声明。

## 使用它

`outputs/skill-memory-auditor.md` 是一项技能，用于审计任何多智能体系统的共享内存设计，检查其是否具备溯源、版本控制和验证器分离。在生产部署新的多智能体架构前请运行它。

## 交付它

对于任何共享内存设计：

- 为每次写入记录溯源信息：`(writer, timestamp, prompt_hash, tool_calls_cited, source_uri)`。
- 使日志仅追加。修正是引用被替代条目的新条目。
- 部署至少一个具有独立来源访问权限的只读验证器智能体。
- 将验证器输出路由到独立通道，而不是反馈回共享池。
- 记录被替代的写入比例——比例上升是幻觉模式的早期证据。

## 练习

1. 运行 `code/main.py`。确认运行 1 传播了幻觉，而运行 2 捕获了它。
2. 添加第二次幻觉：Agent B 虚构了一个数据集大小。验证器应能同时捕获两者，且无需针对任一情况进行手动调优。
3. 将全量消息池切换为带主题分区的黑板（`prices`, `summaries`, `analyses`）。主题分区使哪些投毒场景更难实施，又对哪些场景没有帮助？
4. 阅读 Hayes-Roth (1985, "A Blackboard Architecture for Control")。找出论文中未在本课讨论、但 2026 年系统会受益的两个控制模式。
5. 阅读 CA-MCP (arXiv:2601.11595)。将其 Shared Context Store 映射到 `code/main.py` 中的 MessagePool 或 Blackboard 类。CA-MCP 在此基础上增加了哪些原语？

## 关键术语

| 术语 | 人们常说的 | 实际含义 |
|------|----------------|------------------------|
| Message pool | “共享聊天记录” | 每个智能体读取的仅追加日志。完全透明，扩展性差。 |
| Blackboard | “共享工作区” | 基于主题的发布/订阅。智能体订阅相关主题。扩展性更强。 |
| Provenance | “谁写了什么” | 每次写入的元数据：写入者、时间戳、提示词、来源。 |
| Memory poisoning | “幻觉扩散” | 一个智能体的错误进入共享状态，下游智能体将其当作事实接受。 |
| Append-only | “无原地更新” | 修正是覆盖旧条目的新条目。保留审计轨迹。 |
| Unwritable verifier | “独立审计员” | 只读智能体，负责重新抓取来源并标记不一致之处。 |
| Projection | “作用域视图” | 从全局状态计算的每智能体视图。LangGraph 归约器是典型案例。 |
| Knowledge Source | “专家智能体” | Hayes-Roth 1985 年论文中对黑板参与者的称呼。 |
