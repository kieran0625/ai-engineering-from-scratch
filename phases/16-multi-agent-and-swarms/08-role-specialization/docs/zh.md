# 角色专业化 —— 规划者、批评者、执行者、验证器

> 2026 年最常见的多智能体分解模式：一个智能体负责规划，一个负责执行，一个负责批判或验证。MetaGPT（arXiv:2308.00352）将这一模式形式化为编码进角色提示词的标准作业程序（SOP）——产品经理、架构师、项目经理、工程师、QA 工程师——遵循 `Code = SOP(Team)`。ChatDev（arXiv:2307.07924）通过“对话链”将设计师、程序员、审查员和测试员串联起来，并引入“沟通式去幻觉化”机制（智能体会明确请求缺失的详细信息）。验证器是系统的核心支撑环节：Cemri 等人（MAST, arXiv:2503.13657）指出，所有多智能体失败均可追溯至缺失或失效的验证环节。PwC 报告称，在 CrewAI 中引入结构化验证循环可将准确率提升 7 倍（从 10% 提升至 70%）。

**类型：** 学习 + 构建
**语言：** Python（标准库）
**前置条件：** 第 16 阶段 · 04（基础模型）、第 16 阶段 · 05（监督者）
**耗时：** 约 60 分钟

## 问题

通用的多智能体系统往往产出平庸的结果。群聊里的三个程序员会写出三种风格相同但质量低下的代码。你可以增加更多智能体、增加更多轮次，但仍然无法跨越质量门槛。

解决方案不是增加智能体数量，而是使用*不同*的智能体。分配明确的职责。赋予批评者规划者所不具备的工具。为验证器提供客观的测试套件。这样系统内部就能产生有据可依的分歧与修正，而不仅仅是并行猜测。

## 概念

### 四种经典角色

**规划者（Planner）**。读取目标，生成分步列表或规格说明。工具：知识检索、文档。输出：结构化计划。

**执行者（Executor）**。逐条读取计划步骤，生成最终工件。工具：实际工作工具（代码编译器、Shell、API 客户端）。输出：工件。

**批评者（Critic）**。对照规划者的意图审查执行者的输出。工具：对工件的只读访问权限、静态分析。输出：附带理由的接受/拒绝意见。

**验证器（Verifier）**。读取工件并运行确定性检查。工具：测试运行器、类型检查器、模式验证器。输出：附带证据的通过/失败结果。

批评者是主观的、带有观点的，通常基于 LLM。验证器是客观的、确定性的，通常基于代码。它们不是同一个角色。

### MetaGPT 的 SOP 模式

MetaGPT（arXiv:2308.00352）将软件工程的标准作业程序（SOP）编码为角色提示词：

- **产品经理**编写产品需求文档（PRD）。
- **架构师**生成系统设计。
- **项目经理**拆分任务。
- **工程师**进行实现。
- **QA 工程师**运行测试。

每个角色都有严格的输入/输出模式。角色提示词定义了该角色*是什么*以及它*必须产出什么*。`Code = SOP(Team)` 的表述表明——确定性的 SOP 能将一组 LLM 团队转化为可预测的流水线。

### ChatDev 的沟通式去幻觉化

ChatDev 增加了一个关键机制：当执行者需要计划中未包含的特定细节时，它会在继续之前明确向设计者提问。这防止了 LLM 典型地“合理编造”细节的失败模式。

实现方式：角色提示词中包含“当你需要未被提供的具体信息时，请在输出前按名称询问相关角色。”

### 为什么验证器最为关键

Cemri 等人（MAST）追踪了 1642 起多智能体执行失败案例。其中 21.3% 属于验证缺口——系统交付了无人检查的答案。其余 79% 通常可追溯至“存在检查但静默失败或从未执行”。验证器是系统的核心支撑角色。

PwC 报告（CrewAI 部署，2025 年）称，添加结构化验证循环使准确率从 10% 提升至 70%。仅靠一个角色就实现了 7 倍的提升。

### 批评者与验证器的区别

- 批评者是基于 LLM 对工件进行质量审查的角色。具有主观性。容易被看似合理的文本误导。
- 验证器是在工件上运行的确定性程序。具有客观性。能给出附带证据的通过/失败结果。

两者结合使用。批评者能捕捉验证器无法描述的风格或设计偏好问题。验证器能捕捉批评者看不到的 bug，因为这些 bug 仅在运行时才会显现。

### 反模式

系统中的每个角色都是 LLM，且每个角色的输出都是“看起来不错”。这是典型的 MAST 失败模式。请至少添加一个验证器，其通过/失败判定由代码决定，而非 LLM。

### 框架映射

- **CrewAI** —— `Agent(role, goal, backstory)` 是教科书级别的角色专业化接口。
- **LangGraph** —— 节点可拥有专用提示词；边用于强制执行流水线。
- **AutoGen** —— 在 GroupChat 中使用具有一字名称的、针对特定角色的 ConversableAgents。
- **OpenAI Agents SDK** —— 角色专用 Agent 之间的交接工具。

## 构建它

`code/main.py` 实现了一个四角色流水线，用于构建一个简单的 Python 函数：

- **规划者**生成规格说明。
- **执行者**生成代码字符串。
- **批评者**（模拟 LLM）标记明显问题。
- **验证器**在沙箱（`exec`）中针对测试用例运行生成的代码。

演示运行两次：一次执行者生成正确代码（批评者和验证器均通过），一次执行者生成不符合规格的代码（批评者因代码看似合理而漏掉 bug，验证器因测试失败而捕获它）。

运行：

```
python3 code/main.py
```

## 使用它

`outputs/skill-role-designer.md` 接收一个任务，并生成角色清单（3-5 个角色）、每个角色的输入/输出模式以及验证器检查项。在将智能体接入框架之前使用此工具。

## 交付它

检查清单：

- **至少一个确定性验证器。** 绝不要全依赖 LLM。
- **每个角色明确的 I/O 模式。** 规划者返回规格说明而非散文；执行者读取该模式。
- **沟通式去幻觉化。** 信息缺失时执行者必须向规划者提问；绝不可自行编造。
- **批评者/验证器顺序。** 先运行批评者（成本低，捕获设计问题），后运行验证器（较慢，捕获 bug）。
- **循环预算。** 批评者-执行者修订轮次最多 2 轮，之后升级给人工处理。

## 练习

1. 运行 `code/main.py`，观察验证器如何捕获批评者遗漏的 bug。添加一个静态分析检查（统计 `return` 的出现次数）作为额外的验证器。它能捕获到运行时测试遗漏了什么？
2. 添加第 5 个角色：“需求分析师”，负责将用户愿望转化为规划者可用的规格说明。哪些沟通式去幻觉化请求应向上流转给它？
3. 阅读 MetaGPT 第 3 节（“Agents”）。列出 MetaGPT 的 5 个角色各自的输入/输出模式。
4. 阅读 ChatDev 的对话链图（arXiv:2307.07924 图 3）。指出沟通式去幻觉化在何处打破了一个原本会无限循环的流程。
5. PwC 的 7 倍准确率提升来自验证循环。假设三个添加验证器无益的任务场景——在这些场景中，确定性地检查正确性是不可能的或成本极高。

## 关键术语

| 术语 | 人们常说的 | 实际含义 |
|------|------------|----------|
| 角色专业化 | “不同的智能体，不同的工作” | 针对规划者/执行者/批评者/验证器角色调优的独立系统提示词。 |
| SOP 模式 | “编码的标准作业程序” | MetaGPT 的框架：每个角色严格的 I/O 模式将团队转化为流水线。 |
| 沟通式去幻觉化 | “发明前先询问” | ChatDev 模式：细节缺失时执行者向规划者提问，而非自行编造。 |
| 批评者 | “LLM 审查员” | 主观的、带观点的审查员。能捕捉风格或设计偏好问题。易被看似合理的文本误导。 |
| 验证器 | “确定性检查” | 基于代码的通过/失败判定。测试运行器、类型检查器、模式验证器。不会被误导。 |
| 验证缺口 | “没人检查过” | MAST 失败案例中的 21.3%。交付答案时缺乏能捕获该 bug 的检查。 |
| 修订循环 | “批评者打回重做” | 批评者拒绝会触发执行者带着反馈重新运行。需设定预算。 |
| 全 LLM 反模式 | “看起来不错” | 每个角色都是 LLM，无确定性检查。典型的 MAST 失败模式。 |
