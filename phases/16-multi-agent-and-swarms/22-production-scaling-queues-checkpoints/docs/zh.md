# 生产环境扩展：队列、检查点与持久化执行

> 将多智能体系统扩展到数千个并发运行需要**持久化执行**。LangGraph 的运行时在每个超级步骤（super-step）后写入一个检查点，键为 `thread_id`（默认使用 Postgres）；工作进程崩溃时会释放租约，由另一个工作进程恢复。智能体可以无限期休眠以等待人工输入。**MegaAgent**（arXiv:2408.09955）为每个智能体运行生产者-消费者队列，包含三种状态（空闲/处理中/响应），并采用两层协调机制（组内聊天 + 组间管理聊天）。在 LLM 流式传输场景下，Fiber/异步模型优于“每任务一线程”：线程在等待 token 时 99% 的时间处于空闲状态，而 Fiber 会在 I/O 时协作式让出控制权。反方观点：Ashpreet Bedi 的《Scaling Agentic Software》主张在负载数据证明有必要之前，坚持使用 **FastAPI + Postgres + 别无他物**——简单的架构往往能走得更远。本课程将构建一个持久化的检查点日志、带有状态转换的每智能体工作队列、异步与线程对比演示，并最终落实务实的“从简开始”原则。

**类型：** 学习 + 实践
**语言：** Python（标准库、`asyncio`、`sqlite3`）
**前置知识：** 第 16 阶段 · 09（并行蜂群网络）、第 16 阶段 · 13（共享内存）
**预计时间：** 约 75 分钟

## 问题

原型多智能体系统在单台笔记本电脑上运行良好，三个智能体通过内存事件循环协同工作。当你将其迁移到生产环境时：

- 智能体有时会连续运行数小时（长时间研究、人机协同等待）。
- 工作进程可能崩溃，重启会导致状态丢失。
- 峰值负载是平均值的 10 倍；你需要水平扩展能力。
- 用户按次付费；计费需要精确一次（exactly-once）语义。

内存事件循环无法解决上述任何问题。你需要在其底层构建一个持久化执行层。2026 年的主流方案包括：

1. 带检查点的流程引擎（Temporal、LangGraph 运行时）。
2. 带状态存储的消息队列（Postgres + SQS/RabbitMQ）。
3. Actor 模型框架（MegaAgent 的每智能体生产者-消费者模式）。
4. 手写 FastAPI + Postgres（Bedi 的主张）。

本课程将逐一实现这些方案的微型版本。

## 概念

### 持久化执行：核心模式

持久化执行引擎会在每个“步骤”（LangGraph 称为超级步骤）后持久化完整的程序状态。发生崩溃时：

```
worker crashes mid-step
  -> lease timeout
  -> another worker picks up the thread_id
  -> resumes from last checkpoint
  -> no duplicate side effects
```

要实现此模式，需满足以下要求：

- **可序列化状态。** 所有智能体状态必须可持久化。携带活跃数据库连接闭包无法存活。
- **确定性恢复。** 给定相同的状态和输入，智能体应产生相同的动作（或将 LLM 调用委托给外部确定性预言机）。
- **幂等副作用。** 外部调用（工具调用、支付）必须是幂等的，或使用去重键。

LangGraph 在每个超级步骤后写入检查点；Temporal 在每个活动（activity）后写入；Restate 使用事件溯源日志。三者均实现了同一模式。

### LangGraph 运行时

每个智能体拥有一个 `thread_id`；状态为类型化字典；每个超级步骤向检查点表写入一行。恢复时，运行时从最后一个检查点开始回放，而非从头开始。智能体可以 `interrupt()` 等待人工输入；运行时会持久化状态并释放工作进程。当输入到达时，任意工作进程均可恢复执行。

这是截至 2026 年 4 月的参考生产设计。

### MegaAgent 的每智能体队列

arXiv:2408.09955 描述了一项规模实验：单个集群内运行数千个并发智能体。架构如下：

```
agent i:
  state ∈ {Idle, Processing, Response}
  in_queue   <- messages addressed to agent i
  out_queue  -> replies + side effects

coordinators:
  intra-group chat  (agents in the same group)
  inter-group admin chat  (high-level routing)
```

这种两层协调机制允许组内对话密集进行，同时保持组间通信稀疏——这是在数千个智能体规模下保持成本呈线性增长的关键模式。

### 异步 vs 每任务一线程

LLM 调用属于 I/O 密集型任务。等待下一个 token 的线程 99% 的时间处于空闲状态。每个线程消耗约 1MB 内存；在 10,000 个并发调用下，仅栈空间就需要 10GB。

Fiber（Python 中的 `asyncio`、Go 的 goroutine、Rust 的 `tokio`）会在 I/O 时协作式让出控制权。同样的 10,000 个调用可以轻松容纳在单个进程中。在 LLM 智能体规模下，异步不是优化手段，而是架构本身。

例外情况：CPU 密集型后处理（嵌入生成、tokenizer 技巧等）仍适合使用线程或进程。请将 I/O 层与 CPU 层分离。

### Bedi 的反方观点

《Scaling Agentic Software》（Ashpreet Bedi，2026）指出，大多数团队在未测量实际负载前就过度设计了。务实的默认方案如下：

- FastAPI + Postgres。
- 每次智能体运行对应一行数据；状态通过乐观并发就地更新。
- 后台任务通过 `pg_notify` 或简单的 Celery worker 处理。
- 重试策略直接在应用代码中实现。

对于可管理任务且并发智能体运行数低于约 100 的场景，这通常已足够。只有在实测发现瓶颈时才考虑升级。

核心原则：仅在遇到简单架构无法解决的具体问题时，才引入持久化执行框架。过早引入只会浪费时间在无法带来收益的流程上。

### 精确一次语义

针对计费的智能体运行，你需要实现“有效精确一次”（至少一次投递 + 幂等消费者）。工程实践包括：

- **每次运行使用独立去重键。** 将其包含在每次副作用调用中。
- **发件箱模式（Outbox pattern）。** 副作用先写入表，再由独立进程执行。两步均需保证幂等。
- **补偿事务。** 当副作用成功但追踪写入失败时，安排补偿操作。

这些是数据库工程模式，并非 LLM 特有。LLM 带来的额外开销仅在于调用速度慢；其余均为标准分布式系统问题。

### 彩虹部署（Rainbow Deployment）

Anthropic 的多智能体研究系统采用“彩虹部署”：多个版本的智能体运行时并发运行，这样长生命周期智能体就不必在每次代码发布时被强制终止。在新流量切片上灰度新版本；待旧版本智能体全部完成后退役旧版本。

这在长生命周期有状态系统中已是标准做法；2026 年的新挑战在于智能体可能持续运行数小时，因此发布周期必须予以适配。

### 标准生产环境清单

- 持久化状态（检查点、快照，或发件箱 + 可重放日志）。
- 幂等副作用。
- 面向 LLM 调用的异步 I/O 层。
- 带去重机制的至少一次投递。
- 面向有状态工作负载的彩虹/灰度部署。
- 可观测性：每智能体追踪、超级步骤审计、重试计数器。

## 动手实践

`code/main.py` 实现了以下功能：

- `CheckpointStore` —— 基于 SQLite 的检查点日志，使用 thread_id 作为键。每个超级步骤追加一行。
- `run_with_checkpoint(agent, thread_id)` —— 模拟运行中途崩溃；第二个工作进程从最后一个检查点恢复。
- `AgentQueue` —— 每智能体的空闲/处理中/响应状态机，附带小型工作队列。
- `demo_async_vs_threads()` —— 分别通过 asyncio 和线程运行 500 个并发模拟“LLM 调用”；报告墙钟时间与峰值内存（近似值）。

运行方式：

```
python3 code/main.py
```

预期输出：模拟崩溃后检查点恢复成功；异步版本在 < 1 秒内处理 500 个并发调用；线程版本耗时数秒，且每个并发单元消耗的内存高出数个数量级。

## 交付指南

标准生产环境加固指南：

- **从简开始（Bedi 原则）。** 在实测确认性能瓶颈前，坚持使用 FastAPI + Postgres。
- **优化前先全面埋点。** 记录每次运行的延迟直方图、每步耗时、重试次数及故障分类。
- **副作用采用发件箱模式。** 尤其适用于支付和外部 API 调用。
- **彩虹部署。** 发布期间绝不强制终止正在运行的智能体。
- **仅在遇到特定问题时引入持久化执行引擎（Temporal / LangGraph / Restate）：** 如长达数小时的人机协同等待、跨区域协调、复杂的重试/补偿策略。
- **I/O 层全面异步。** 线程仅用于 CPU 密集型后处理。

## 练习

1. 运行 `code/main.py`。确认检查点恢复功能正常；测量异步与线程在并发处理上的差异。
2. 实现**发件箱（outbox）**表：每次工具调用先写入该表，再由独立的 goroutine/任务执行。通过重复执行两次该工具调用验证幂等性。
3. 模拟**彩虹部署**：两个并发的运行时版本；将新 thread_id 的一半路由至各版本；确认旧版本上正在运行的线程未受中断。
4. 阅读 LangGraph 的运行时文档（见下方链接）。找出在手动实现的 FastAPI + Postgres 版本中最难复现的运行时特性。这是否构成引入的理由，还是可以推迟？
5. 阅读 MegaAgent（arXiv:2408.09955）第 3 节。其中明确提到了两层协调机制（组内 + 组间管理聊天）。请草绘你将如何将其映射到具有两类队列族的消息队列中。

## 关键术语

| 术语 | 常见说法 | 实际含义 |
|------|----------|----------|
| Durable execution | “持久化程序状态” | 引擎在每个超级步骤后写入状态；崩溃恢复具有确定性。 |
| Super-step | “事务边界” | 检查点之间的工作单元。LangGraph 术语。 |
| thread_id | “智能体运行标识符” | 绑定检查点与恢复逻辑的键。 |
| Idempotency | “可安全重试” | 重复执行副作用产生的结果与单次尝试一致。 |
| Outbox pattern | “解耦副作用” | 先将意图写入表；由独立执行器执行并标记完成。 |
| At-least-once delivery | “可能存在重复” | 消息队列语义；配合去重键可使消费者实现有效一次。 |
| Rainbow deploy | “版本重叠” | 长生命周期工作负载期间，多个运行时版本并发运行。 |
| Async fiber | “协作式让出” | 用户态并发；相比线程，在 I/O 密集型负载下开销更低。 |
| Checkpoint | “状态快照” | 超级步骤边界的序列化状态；用于恢复的键。 |
