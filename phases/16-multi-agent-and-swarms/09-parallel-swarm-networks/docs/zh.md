# 并行 / 群体 / 网络化架构

> 与 Supervisor 模式对比：无中央决策器。智能体读取共享的事件总线，异步领取任务，并将结果写回。LangGraph 明确支持用于去中心化、动态环境的“Swarm Architecture（群体架构）”。Matrix（arXiv:2511.21686）将控制流和数据流均表示为通过分布式队列传递的序列化消息，以消除编排器的瓶颈。其权衡非常明确：以牺牲确定性和可追溯性为代价，换取可扩展性。群体架构适合包含大量独立子问题的任务；它不适合需要单一连贯计划的任务。

**类型：** 学习 + 构建
**语言：** Python（stdlib、`threading`、`queue`）
**前置要求：** Phase 16 · 05（Supervisor Pattern）、Phase 16 · 04（Primitive Model）
**耗时：** 约 75 分钟

## 问题

Supervisor 模式可扩展到少数几个工作节点。那如果是成百上千个呢？Supervisor 本身会成为瓶颈：关于“谁做什么”的每一个决策都必须经过一个智能体。一个缓慢的计划步骤就会卡住整个系统。

群体架构颠覆了这种设计。工作节点不再由中央规划器分发任务，而是从共享队列中自行领取。所谓的“协调”直接内嵌在事件总线的语义中。没有编排器；系统的扩展能力取决于队列的承载上限。

## 概念

### 结构形态

```
                ┌──── shared queue ────┐
                │                      │
       ┌────────┼────────┐  ◄──────┬───┘
       ▼        ▼        ▼         │
     Worker  Worker  Worker   Worker
      A       B       C        D
       │        │        │         │
       └────────┴────────┴─────────┘
                 │
                 ▼
            results pool
```

无编排器。每个工作节点循环执行：领取任务、处理、写入结果（并可选地将后续任务入队）。

### 适用场景

- **大量独立任务。** 如数据抓取、转换、分类。任务之间互不依赖。
- **时长不一的工作。** 如果部分任务耗时 100ms，另一些耗时 10s，群体架构会自动平衡负载——快速的工作节点会立即领取下一个任务。而 Supervisor 必须预先预估任务时长。
- **吞吐量优先于确定性。** 你关注的是整体完成时间，而非严格的执行顺序。

### 不适用场景

- **有序工作流。** 如果第 3 步需要第 2 步的输出，群体架构可能导致第 3 步在第 2 步完成前就触发。
- **全局规划型任务。** 复杂的研究问题受益于规划器。一群研究人员组成的群体只能产出独立的事实片段，而无法生成连贯的报告。
- **调试困难。** 缺乏集中式日志且任务异步执行时，复现 Bug 的成本很高。

### Matrix（arXiv:2511.21686）

Matrix 是 2025 年的一篇论文，它将群体架构推向了自然结论：控制流和数据流均为分布式队列上的序列化消息。没有中央协调器。容错性来源于消息的持久化。可扩展性则是消息代理（message broker）的问题，而非系统本身的问题。

核心贡献：提出了一种编程模型，其中多智能体协调机制变为“该智能体订阅了哪些消息主题？”，而不是“Supervisor 下一步会选择哪个智能体？”。这使得系统看起来像一个发布/订阅（pub/sub）事件网格。

### LangGraph 的群体架构

LangGraph 2025 年的文档明确将“Swarm Architecture”列为多智能体模式之一：智能体作为节点，但边构成带有环路的有向图，且池中的任何节点均可被激活。工作节点根据条件从可用任务中选取，而非由 Supervisor 分配。

### 故障模式：饥饿与热点聚集

如果所有工作节点都只领取当前最快的任务，长耗时任务将永远无法被领取，直到它们成为队列中仅剩的任务。这是典型的队列饥饿现象。

缓解措施：
- 带显式老化机制的优先级队列（等待时间越长，优先级越高）。
- 工作节点专业化：部分工作节点仅处理“长耗时”任务。
- 背压（Back-pressure）：限制进入队列的快速任务数量。

### 基于内容的路由关联

群体架构天然契合基于内容的路由（第 22 课）。与其使用通用队列，不如为每种消息类型设立独立的队列。专业工作节点仅订阅其对应的类型。这是支撑数千个智能体规模的消息总线架构的基础。

## 动手实现

`code/main.py` 实现了一个由 4 个工作线程组成的群体，它们从共享的 `queue.Queue` 中拉取任务。任务具有不同的耗时（部分快，部分慢）。该演示对比了以下三种方式：

- **串行基线：** 单个工作节点串行处理所有任务。
- **固定分配：** 每个任务预先分配给特定工作节点（类似 Supervisor 模式）。
- **群体架构：** 工作节点从共享队列中自主拉取任务。

群体架构会自动平衡负载；而固定分配模式下，当某个工作节点被分配的任务耗时较长时，其他快速工作节点将处于空闲状态。

运行命令：

```
python3 code/main.py
```

输出将显示各工作节点的任务处理数量（群体架构分布不均但最优）以及墙钟时间。

## 实际应用

`outputs/skill-swarm-fit.md` 用于评估任务应使用群体架构还是 Supervisor 模式。输入参数包括：任务独立性、时长方差、排序要求、调试需求。

## 生产部署清单

检查清单：

- **带老化机制的优先级队列。** 防止长耗时任务饥饿。
- **工作节点幂等性。** 若工作节点在运行中途崩溃，任务可能被重复拉取。工作节点必须具备幂等性。
- **持久化队列。** 生产环境请使用 Kafka、Redis Streams 或基于数据库的队列。`queue.Queue` 仅支持内存存储。
- **任务级可观测性。** 每个任务分配唯一的 Trace ID；每个工作节点记录任务的开始与结束时间。
- **背压机制。** 如果队列增长速度超过工作节点的消费速度，需减缓生产者速率。

## 练习

1. 运行 `code/main.py`。在时长不一的工作负载下，群体架构比串行模式快多少？比固定分配模式快多少？
2. 添加优先级队列变体（使用 `queue.PriorityQueue`）。根据任务的 “importance” 字段分配优先级。观察在持续负载下，低优先级任务是否会出现饥饿现象。
3. 实现热点检测器：记录任意工作节点处理的任务数达到最慢工作节点 3 倍时的日志。这反映了任务时长分布的什么特征？
4. 阅读 Matrix 论文（arXiv:2511.21686）的摘要和第 3 节。指出 Matrix 接受的一个具体权衡（可扩展性提升）以及放弃的一个特性（可追溯性或确定性）。
5. 将群体架构演示转换为使用 `queue.Queue` 存储 `(task_type, payload)` 元组，工作节点仅订阅特定类型。当任务异构时，什么样的路由规则更合理？

## 关键术语

| 术语 | 常见说法 | 实际含义 |
|------|----------|----------|
| Swarm architecture（群体架构） | “去中心化智能体” | 工作节点从共享队列拉取任务；无中央编排器。 |
| Event bus（事件总线） | “智能体订阅主题” | 按类型或内容将任务路由至工作节点的消息代理。 |
| Starvation（饥饿） | “任务永不执行” | 由于高优先级任务持续到达，低优先级任务永远无法被领取。 |
| Hot-spotting（热点聚集） | “单个工作节点过载” | 负载不均，导致某个工作节点承担了大部分任务。 |
| Back-pressure（背压） | “减缓生产者” | 当队列满溢时，向上游发送信号停止生产的机制。 |
| Idempotent worker（幂等工作节点） | “可安全重跑” | 任务被执行两次产生相同的结果。因工作节点可能中途崩溃，此特性为必需。 |
| Durable queue（持久化队列） | “抗崩溃” | 基于磁盘或副本存储的队列；工作节点崩溃时任务不会丢失。 |
| Matrix framework（Matrix 框架） | “全消息传递群体” | 数据流与控制流均为分布式队列上的序列化消息。 |
