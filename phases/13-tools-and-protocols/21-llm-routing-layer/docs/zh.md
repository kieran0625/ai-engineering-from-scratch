# LLM 路由层 —— LiteLLM、OpenRouter、Portkey

> 供应商锁定成本高昂。不同的工具调用工作负载适合不同的模型。路由网关提供统一的 API 接口、重试机制、故障转移、成本追踪和护栏功能。2026 年主导市场的三大架构为：LiteLLM（开源自托管）、OpenRouter（托管 SaaS）以及 Portkey（生产级，于 2026 年 3 月开源）。本课将明确决策标准，并逐步实现一个基于标准库的路由网关。

**类型：** 学习
**语言：** Python（标准库，路由 + 故障转移 + 成本追踪）
**前置知识：** 阶段 13 · 02（函数调用）、阶段 13 · 17（网关）
**预计时间：** 约 45 分钟

## 学习目标

- 区分自托管、托管和生产级路由方案。
- 实现回退链，在定义优先级顺序下对提供商故障进行重试。
- 跨不同提供商追踪单次请求的成本与 Token 用量。
- 根据特定的生产环境约束，在 LiteLLM、OpenRouter 和 Portkey 之间做出选择。

## 问题背景

需要提供商路由的场景包括：

1. **成本。** Claude Sonnet 的价格是 Haiku 的 3 倍。对于分诊任务，Haiku 已足够；对于综合任务，Sonnet 物有所值。按请求进行路由。

2. **故障转移。** OpenAI 出现服务异常时段。所有请求均失败。你希望在不重新部署的情况下自动回退到 Anthropic。

3. **延迟。** 实时聊天界面需要极快的首字生成时间。批量摘要器则不需要。按延迟 SLA 进行路由。

4. **合规性。** 欧盟用户的数据必须保留在欧盟境内。按地域进行路由。

5. **实验测试。** 在同一工作负载上对两个模型进行 A/B 测试。按测试分组进行路由。

为每个集成单独手写实现这些逻辑非常繁琐。路由网关提供统一的 OpenAI 兼容 API，并处理其余所有逻辑。

## 核心概念

### OpenAI 兼容的代理形态

业界普遍采用 OpenAI 格式。路由网关暴露 `/v1/chat/completions`，接受 OpenAI 模式，并在内部代理转发至 Anthropic / Gemini / Cohere / Ollama 或其他任何后端。客户端无需关心底层差异。

### 模型别名

代码中不再使用 `claude-3-5-sonnet-20251022`，而是使用 `our_smart_model`。网关负责将别名映射到实际模型。当 Anthropic 发布 Claude 4 时，你只需在服务端更改别名映射；你的代码完全无需修改。

### 回退链

```
primary: openai/gpt-4o
on 5xx: anthropic/claude-3-5-sonnet
on 5xx: google/gemini-1.5-pro
on 5xx: refuse
```

网关通过配置文件定义此逻辑。重试次数计入预算限制，以防止回退级联导致成本失控。

### 语义缓存

相同或高度相似的提示词命中缓存而非直接发送给提供商。在重复的 Agent 循环中，节省成本可达 30% 至 60%。缓存键基于 Embedding 生成；高度相似的提示词共享同一个缓存槽位。

### 护栏功能

网关层面：

- **PII（个人身份信息）脱敏。** 发送提示词前进行正则或基于机器学习的过滤。
- **策略违规拦截。** 拒绝包含禁止内容的提示词。
- **输出过滤。** 清理完成内容中的信息泄露风险。

Portkey 和 Kong 均内置了明确的护栏功能。LiteLLM 则将其设为可选配置。

### 按密钥限流

一个 API 密钥对应一个团队。按密钥设置预算可防止单个团队耗尽共享配额。大多数网关支持此功能。

### 自托管与托管的权衡

| 考量因素 | LiteLLM（自托管） | OpenRouter（托管） | Portkey（生产级） |
|--------|----------------------|----------------------|----------------------|
| 代码/授权 | 开源，Python | 托管 SaaS | 开源（2026年3月）+ 托管 |
| 部署方式 | 部署代理服务器 | 注册账号 | 两者皆可 |
| 支持提供商 | 100+ | 300+ | 100+ |
| 计费方式 | 使用自有密钥 | OpenRouter 积分 | 使用自有密钥 |
| 可观测性 | OpenTelemetry | 仪表盘 | 完整 OTel + PII 脱敏 |
| 适用场景 | 需要完全控制权的团队 | 快速原型开发 | 需要合规的生产环境 |

当你拥有 SRE 团队且重视数据主权时，LiteLLM 是最佳选择。当你希望单一订阅且无需维护基础设施时，OpenRouter 胜出。当你开箱即用需要护栏功能和合规支持时，Portkey 更合适。

### 成本追踪

每次请求都携带 `provider`、`model`、`input_tokens`、`output_tokens`。将其乘以各模型每 Token 的价格（价格表由网关维护）。支持按用户/团队/项目维度聚合统计。

### MCP 与路由结合

网关可以同时路由 LLM 调用和 MCP 采样请求。当采样请求的 modelPreferences 偏好特定模型时，网关会将其翻译并转发至正确的后端。这正是阶段 13 · 17（MCP 网关）与本课路由网关有时会合并为同一服务的场景。

### 路由策略

- **静态优先级。** 列表首位优先；出错时降级。
- **负载均衡。** 轮询或加权分配。
- **成本感知。** 选择满足延迟/质量要求的最低成本模型。
- **延迟感知。** 选择过去 N 分钟内响应最快的模型。
- **任务感知。** 提示词分类器将编程类任务路由至一个模型，摘要类任务路由至另一个模型。

## 实践应用

`code/main.py` 用约 150 行代码实现了一个路由网关：接受 OpenAI 格式的请求，转换为各提供商的存根调用，执行优先级回退链，追踪单次请求成本，并对输入执行 PII 脱敏流程。使用以下三种场景运行它：正常请求、主提供商宕机触发回退、PII 泄露被脱敏拦截。

重点关注：

- `ROUTES` 字典：别名映射到按优先级排序的具体提供商列表。
- 回退循环在遇到 5xx 错误时重试。
- 成本追踪器将 Token 用量乘以各模型单价。
- PII 脱敏器在转发前清除类似社保号（SSN）的敏感模式。

## 练习

1. 运行 `code/main.py`。触发宕机场景；确认回退成功切换至第二个提供商，且成本正确归因。

2. 添加语义缓存：将提示词的 SHA256 作为查找键；缓存命中时立即返回。测量重复调用时的成本节省情况。

3. 添加提示词分类器：将 "code ..." 类提示词路由至偏向智能的别名，将 "summarize ..." 类提示词路由至偏向速度的别名。

4. 设计按团队预算：每个团队设有月度支出上限；网关在达到上限后拒绝请求。选择执行粒度（按次或滑动窗口）。

5. 对照阅读 LiteLLM、OpenRouter 和 Portkey 的文档。指出各自独有而其他两家不具备的一项功能。
