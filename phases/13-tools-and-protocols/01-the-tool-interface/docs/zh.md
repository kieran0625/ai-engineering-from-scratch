# 工具接口 —— 为什么 Agent 需要结构化 I/O

> 语言模型生成 token。程序执行动作。两者之间的鸿沟就是工具接口：一种让模型请求动作、宿主（host）执行它的契约。每一个 2026 技术栈——OpenAI、Anthropic 和 Gemini 的函数调用；MCP 的 `tools/call`；A2A 的任务部件——都是对同一个四步循环的不同编码。本课将命名该循环，并展示运行它所需的最简机制。

**类型：** 学习
**语言：** Python（标准库，无需 LLM）
**前置知识：** 第 11 阶段（LLM 补全 API）
**耗时：** 约 45 分钟

## 学习目标

- 解释为何仅能生成文本的 LLM 无法自行对现实世界采取行动。
- 绘制四步工具调用循环（描述 → 决策 → 执行 → 观察），并明确每一步的归属方。
- 编写包含三个部分的内容来描述工具：名称、JSON Schema 输入参数，以及确定性执行器函数。
- 区分纯函数工具与副作用工具，并说明这种划分对安全性的意义。

## 问题所在

LLM 会输出下一个 token 的概率分布。这就是其全部的输出能力。如果你问聊天模型“班加罗尔现在的天气如何”，它能写出一句看似合理的话，但无法直接调用天气 API。这句话可能只是巧合说对了，或者已经是三天前的过时信息。

填补这一鸿沟正是工具接口的目的。宿主程序——你的 Agent 运行时、Claude Desktop、ChatGPT、Cursor 或自定义脚本——会向模型声明一个可调用工具列表。当模型判断需要采取动作时，会输出一个结构化的负载（payload），指明要调用的工具及其参数。宿主解析该负载，真实地执行工具，并将结果反馈回去。循环将持续进行，直到模型判断不再需要调用为止。

该契约的第一个版本于 2023 年 6 月随 OpenAI 的“functions”参数发布。Anthropic 随后在 Claude 2.1 中推出了 `tool_use` 块。几个月后，Gemini 也添加了 `functionDeclarations`。如今每个提供商都暴露出相同的结构：输入为 JSON Schema 类型的工具列表，输出为 JSON 格式的工具调用负载。Model Context Protocol（2024 年 11 月）将该契约泛化，使得一个工具注册表即可服务所有模型。A2A（2026 年 4 月，v1.0）则在相同原语之上构建了 Agent 间委托机制。

四步循环是这一切背后的不变量。第 13 阶段的其余内容都是对该循环的展开说明。

## 核心概念

### 第一步：描述

宿主使用三个字段声明每个工具。

- **名称（Name）。** 稳定且机器可读的标识符。例如 `get_weather`，而不是“天气相关东西”。
- **描述（Description）。** 一段自然语言的简要说明。“当用户询问特定城市的当前状况时使用。不要用于历史数据。”
- **输入模式（Input schema）。** 描述工具参数的 JSON Schema 对象（draft 2020-12 草案）。

模型接收该列表。现代提供商会使用特定模板将这些声明序列化到系统提示词中，因此作为调用方的你只需处理结构化形式。

### 第二步：决策

给定用户消息和可用工具，模型会选择以下三种行为之一。

1. **直接回答。** 以文本形式回复，不调用工具。
2. **调用一个或多个工具。** 输出结构化的调用对象。在 `parallel_tool_calls: true` 模式下（OpenAI 和 Gemini 默认开启，Anthropic 需手动选择），模型可以在单轮对话中发出多个调用。
3. **拒绝。** 严格模式的结构化输出可能会生成一个类型化的 `refusal` 块，而不是调用对象。

工具调用负载包含三个稳定字段：调用 ID（`id`）、工具名（`name`）和一个 JSON 参数对象（`arguments`）。ID 的存在是为了让宿主能够将后续结果与特定的调用关联起来，这在并行调用返回顺序不一致时尤为重要。

### 第三步：执行

宿主接收调用，根据声明的模式验证参数，然后运行执行器。无效参数意味着模型幻觉出了不存在的字段或使用了错误的类型——这在较弱模型上是非常常见的失败模式。生产环境的宿主会对无效参数采取以下三种措施之一：快速失败并将错误反馈给模型、使用约束解析器修复 JSON，或将验证错误加入提示词并重试模型。

执行器本身只是普通代码。可以是 Python、TypeScript、Shell 命令或数据库查询。它会产出一个结果，通常是字符串，也可以是任何 JSON 值或结构化内容块（MCP 中的文本、图片或资源引用）。结果必须是可序列化的。

### 第四步：观察

宿主将工具结果追加到对话中（作为带有匹配 `id` 的 `tool` 角色消息），并重新调用模型。此时模型已在上下文中获得了工具输出，可以生成最终答案或请求更多调用。此过程将持续进行，直到模型停止发出调用，或宿主达到迭代次数的安全限制。

### 信任划分

工具分为两种对安全性至关重要的类型。

- **纯函数（Pure）。** 只读、确定性、无副作用。例如 `get_weather`、`search_docs`、`get_current_time`。可以安全地进行推测性调用。
- **后果性（Consequential）。** 改变状态、消耗资金、接触用户数据。例如 `send_email`、`delete_file`、`execute_trade`。必须设置访问控制门控。

Meta 在 2026 年提出的 Agent 安全“双规则”指出，单次交互最多只能组合以下三项中的两项：不可信输入、敏感数据、后果性操作。工具接口正是你执行该规则的地方——通过拒绝调用、要求用户确认或提升权限范围来实现。完整的安全章节请参阅第 13 阶段 · 15，Agent 级权限策略请参阅第 14 阶段 · 09。

### 循环的运行位置

| 上下文环境 | 谁负责描述 | 谁负责决策 | 谁负责执行 |
|---|---|---|---|
| 单轮函数调用（OpenAI/Anthropic/Gemini） | 应用开发者 | LLM | 应用开发者 |
| MCP | MCP 服务器 | 通过 MCP 客户端的 LLM | MCP 服务器 |
| A2A | Agent Card 发布者 | 发起调用的 Agent | 被调用的 Agent |
| Web 浏览器（支持函数调用的 Agent） | 浏览器扩展 / WebMCP | LLM | 浏览器运行时 |

无论在哪种环境下，都是同样的四个步骤。列名会变，但结构不变。

### 为什么不直接提示模型输出 JSON？

“要求模型以 JSON 格式回复”是函数调用出现之前的旧模式。它在前沿模型上的失败率约为 5% 到 15%，在小模型上则高得多。失败模式包括缺少花括号、尾部逗号、幻觉出的字段以及错误的类型。随后你需要进行 JSON 修复、重试或使用约束解码器。

原生函数调用更好，原因有三。首先，提供商针对精确的调用形状对模型进行了端到端训练，因此在严格模式下有效 JSON 的输出率可提升至 98% 到 99%。其次，调用负载位于独立的协议槽位中，而非嵌入自由文本——因此工具调用永远不会泄露到用户可见的回复中。第三，提供商通过约束解码强制执行模式合规性（OpenAI 的严格模式、Anthropic 的 `tool_use`、Gemini 的 `responseSchema`）。输出保证能通过验证。

第 13 阶段 · 02 将并列讲解这三个提供商的 API。第 13 阶段 · 04 将深入探讨结构化输出。

### 熔断器

当模型停止发出调用，或宿主达到最大轮数限制时，循环终止。生产环境的宿主通常将此限制设置为 5 到 20 轮。超过这个数量，你几乎肯定陷入了模型无法退出的死循环。Claude Code 默认为 20；OpenAI Assistants 为 10；Cursor 的 Agent 模式为 25。

另一种情况——无界循环——每半年就会以“Agent 一夜之间花费 400 美元 API 调用费”的事故复盘形式出现。切勿在未设置上限的情况下上线。

## 动手实践

`code/main.py` 在无 LLM 的情况下运行四步循环。一个伪造的“决策器”函数通过对用户消息进行模式匹配来模拟模型；而执行器、模式验证器和观察步骤的测试框架则是真实的。运行它以查看带有可打印中间状态的完整请求/响应编排，然后在后续课程中将伪造的决策器替换为任意真实的提供商。

重点关注：

- 工具注册表为每个工具保存字段：名称、描述、模式，以及执行器引用。
- 验证器是一个极简的 JSON Schema 子集（仅包含 types、required、enum、min/max），完全使用标准库编写。第 13 阶段 · 04 会提供功能更完整的版本。
- 循环将迭代次数限制为五次。生产环境的 Agent 正需要这种类型的熔断器。

## 练习

1. 向 `code/main.py` 添加第四个工具，命名为 `get_stock_price(ticker)`。将其描述写为：“当用户按股票代码查询当前股价时使用。不要用于历史价格或市场摘要。”运行测试框架，并确认伪造的决策器能将提及股票代码的查询路由到新工具。

2. 破坏模式验证器。传入一个其 `arguments` 对象缺少必填字段的调用，并确认宿主在执行前拒绝了它。然后传入一个带有额外未知字段的调用。做出决定：宿主应该拒绝还是忽略？请用安全论证来证明你的选择。

3. 将测试框架中的每个工具分类为纯函数或后果性。为需要的注册表条目添加 `consequential: true` 标志，并修改循环逻辑，每当选择后果性工具时打印一行“will confirm with user”（将向用户确认）。这就是每个生产环境宿主所需的确认门控形态。

## 关键术语

| 术语 | 人们常说的说法 | 实际含义 |
|---|---|---|
| 工具（Tool） | “模型可以调用的东西” | 由名称 + JSON Schema 类型输入 + 执行器函数组成的三元组 |
| 函数调用（Function calling） | “原生工具使用” | 提供商级别的 API 支持，用于输出结构化工具调用而非纯文本 |
| 工具调用（Tool call） | “模型发出的行动请求” | 模型输出的包含 `id`、`name`、`arguments` 的 JSON 负载 |
| 工具结果（Tool result） | “工具返回的内容” | 执行器的输出，包装在带有匹配 ID 的 `tool` 角色消息中 |
| 并行工具调用（Parallel tool calls） | “同时发起多次调用” | 单次模型交互中的多个调用对象，相互独立且可通过 ID 排序 |
| 严格模式（Strict mode） | “保证 JSON 格式” | 约束解码机制，强制模型的输出必须符合声明的模式 |
| 纯工具（Pure tool） | “只读工具” | 无副作用；可安全重复运行 |
| 后果性工具（Consequential tool） | “动作工具” | 改变外部状态；需要门控、审计或用户确认 |
| 四步循环（Four-step loop） | “工具调用周期” | 描述 → 决策 → 执行 → 观察 |
| 宿主（Host） | “Agent 运行时” | 持有工具注册表、调用模型并运行执行器的程序 |
