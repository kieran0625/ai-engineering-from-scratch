# 百万 Token 上下文下的长视频理解

> 一段 1 小时、24 FPS 的 4K 视频，经过分块（patching）和嵌入后，会产生约 6000 万个 token。一段转录后的 2 小时播客约为 30,000 个 token。一部完整的蓝光电影，即使采用激进的池化压缩，也有数十万个 token。Google 的 Gemini 1.5（2024年3月）以 1000 万 token 的上下文开启了这一时代，能够在长达数小时的视频中实现可靠的“大海捞针”召回。LWM（Liu 等人，2024年2月）展示了环形注意力（ring attention）的扩展路径。LongVILA 和 Video-XL 进一步扩展了数据摄入规模。VideoAgent 则用智能体检索替代了原始上下文。每种方法在计算资源、召回率和工程复杂度之间做出了不同的权衡。本课程将并排解析这些方案。

**类型：** 构建
**语言：** Python（标准库，含大海捞针模拟器 + 智能体检索路由器）
**前置要求：** 第 12 阶段 · 第 17 课（视频时间 token）
**预计时长：** 约 180 分钟

## 学习目标

- 计算不同帧率（FPS）和池化策略下长视频的总视觉 token 数量。
- 解释三种扩展路径：暴力上下文（Gemini 1.5）、环形注意力（LWM）、Token 压缩（LongVILA / Video-XL）。
- 对比原始上下文视频 VLM 与智能体检索视频 VLM（VideoAgent）在准确率和延迟方面的表现。
- 为 30 分钟视频设计“大海捞针”测试，并测量特定时间点的召回率。

## 问题背景

在 384 原生分辨率下，单帧 Qwen2.5-VL 尺寸的分块图像约为 729 个 token。经过 3x3 池化后，每帧为 81 个 token。一段 30 分钟、1 FPS 的视频片段 = 1800 帧 = 145,800 个 token。2025 年的开源 VLM 可以处理，但已接近极限。若为 2 FPS，则达到 291,600 个 token —— 仅最大上下文的模型才能容纳。

一段 2 小时、1 FPS 的电影约为 58.3 万 token。这超出了大多数 2026 年开源模型的承载范围；需要依赖 Gemini 2.5 Pro 或采用更激进的池化策略。

由此衍生出三条扩展路径。

## 核心概念

### 路径 1：暴力上下文（Gemini 1.5、Claude Opus）

直接堆硬件解决。将上下文扩展至数百万 token，在一次前向传播中处理所有内容。

Gemini 1.5 Pro 首发支持 100 万 token；Gemini 1.5 Ultra 支持 1000 万；2026 年的 Gemini 2.5 Pro 可稳定处理数小时的视频。相关论文（arXiv:2403.05530）记录显示，在约 950 万 token 范围内，“大海捞针”召回率可达 99.7%。

工程实现：采用自定义注意力机制，结合内存层级结构（局部 + 全局 + 稀疏），并辅以 MoE 专家路由以提升长上下文效率。未公开完整细节，且非开源。

### 路径 2：环形注意力（LWM、LongVILA）

环形注意力将长序列分布在多个设备组成的“环”上，每个设备持有序列的一个分块。全序列的注意力计算通过每个设备按环形模式将分块发送给下一台设备、计算部分注意力并进行聚合来实现。

LWM（Liu 等人，2024）以此方式训练了支持 100 万 token 上下文的模型。训练算力随上下文线性增长，而非二次方增长——注意力的二次方开销被分摊到环上的各个设备中。

LongVILA（arXiv:2408.10188）将该模式适配至 VLM。其处理 1400 帧视频（每帧 192 token，共 26.8 万上下文），并在 8 路并行下使用环形注意力进行训练。

### 路径 3：Token 压缩（Video-XL、LongVA）

比暴力上下文成本更低：在 LLM 看到序列之前进行激进压缩。

Video-XL（arXiv:2409.14485）使用视觉摘要 token：每个包含 N 帧的片段生成一个单一的“摘要”token，该 token 会对这 N 帧进行注意力计算。推理时，LLM 每个片段仅看到一个摘要 token，从而大幅缩减上下文长度。

LongVA 通过“长上下文迁移”技术将 LLM 上下文从 20 万扩展至 200 万。先在长文本上进行训练，再通过共享表示层迁移至长视频上下文。

Token 压缩以牺牲特定时间戳的召回率为代价换取可扩展性。模型能大致了解发生了什么，但有时会遗漏精确帧。

### 路径 4：智能体检索（VideoAgent）

不将完整视频输入 LLM。相反，将视频视为数据库，利用 LLM 进行查询。

VideoAgent（arXiv:2403.10517）的工作流程：

1. LLM 读取用户问题。
2. LLM 调用检索工具获取相关片段（例如：“展示有猫的片段”）。
3. 工具返回匹配的片段时间戳。
4. LLM 通过 VLM 读取这些片段。
5. LLM 组合答案或发起后续查询。

这是将“LLM 作为智能体”模式应用于长视频的方案。推理成本更低（仅编码相关片段），但工程难度更高（检索质量成为瓶颈）。

### “大海捞针”基准测试

标准的长上下文测试方法：在视频中随机位置插入独特的视觉或文本标记，然后提出需要回忆该标记的查询。

评估指标：在不同视频长度和标记位置下的 Recall@k。

Gemini 2.5 Pro 在长达 90 分钟的视频中召回率超过 99%。开源 72B 模型（Qwen2.5-VL-72B、InternVL3-78B）在 30 分钟时得分约 85-90%，超过 60 分钟后性能下降。

对于 2 小时以上的视频，VideoAgent 能够持平甚至超越原始上下文模型，因为只要检索工具足够好，就能精准命中目标。

### 如何选择路径

针对 15 分钟片段且追求前沿准确率：开源 72B 模型 + 原生上下文通常即可胜任。推荐选择 Qwen2.5-VL-72B。

针对 30 分钟至 1 小时内容：开源方案可选 LongVILA 或 Video-XL；闭源方案选 Gemini 2.5 Pro。质量门槛是关键——前沿能力往往依赖闭源模型。

针对 2 小时以上长内容：选用 VideoAgent 或类似的检索模式。或者，将其总结为较小的片段并输入分层摘要。

### 2026 年生产环境模式

在实际生产中，长视频流水线通常采用混合架构：

1. 对整个视频运行动态 FPS 采样 + 激进池化（获得 10 万 token 的全局表示）。
2. 输入至 72B VLM 生成全局摘要。
3. 若用户提出详细问题，则以摘要为索引运行智能体检索。

该方案结合了暴力上下文的全局理解能力与检索的局部细节处理能力。

## 关键术语

| 术语 | 常见说法 | 实际含义 |
|------|----------|----------|
| Brute context（暴力上下文） | “就是更多 token” | 将 LLM 上下文扩展至数百万 token；单次前向传播处理全部内容 |
| Ring attention（环形注意力） | “LWM 风格并行” | 分布式注意力模式，每个设备持有序列分块并进行轮换 |
| Token compression（Token 压缩） | “摘要 token” | 在 LLM 处理前，通过学习型压缩器减少每个片段的 token 数量 |
| Needle-in-a-haystack（大海捞针） | “NIH 测试” | 在随机位置插入唯一标记，测试时要求模型回忆该标记 |
| Agentic retrieval（智能体检索） | “LLM 作为查询规划器” | LLM 调用检索工具获取相关片段，通过 VLM 读取并组合答案 |
| VideoAgent | “视频检索模式” | 标准的智能体检索架构：问题 -> 工具 -> 片段 -> 答案 |
