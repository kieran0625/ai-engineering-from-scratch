# 分块策略对比

> 分块（Chunking）决定了检索器能够召回的内容边界。如果切分边界设置错误，后续的嵌入模型、重排序器或 LLM 都无法弥补下游的损失。

**类型：** 构建实践
**语言：** Python
**前置知识：** Phase 11 课程 04（嵌入）、06（RAG）、07（高级 RAG）；Phase 19 Track B 基础（课程 20-29）
**预计时间：** 约 90 分钟

## 学习目标
- 从零实现五种分块策略：固定窗口、句子级、递归分割、语义聚类和基于结构化的 Markdown 标题。
- 在带有黄金标注答案片段的测试语料库上测量 recall@k，并解释为何一种策略在散文类文本上表现更好，而另一种在技术文档上更优。
- 解读分块长度分布，识别每种策略引入的失效模式：孤立句子、符号中间截断、仅含标题的分块、语义漂移。
- 在不运行基准测试的情况下，通过检查三个属性（文档类型、平均段落长度、格式是否包含显式结构）为新语料库选择默认策略。

## 问题背景

每个 RAG 流水线的第一步都是将源文档切割成足够小的片段，以便嵌入模型能够处理，同时又足够大以承载一个完整的独立概念。在哪里切分并非一个超参数问题，它决定了检索器能返回内容的上限。

如果查询是“预算中止阈值是什么样的”，只有当包含该阈值的分块可被检索到时，查询才能成功。如果固定窗口分割器将阈值与其上下文割裂开来，嵌入向量会落入错误的聚类簇，BM25 得分下降，重排序器接收到噪声，最终 LLM 生成的答案就会出错。2024 年的论文《LongRAG: Enhancing Retrieval-Augmented Generation with Long-context LLMs》指出，仅因分块策略的不同，检索召回率就会出现高达 35% 的绝对波动。2025 年关于上下文分块头（contextual chunk headers）的后续研究缩小了这一差距，但并未完全消除。

本课程将并行实现五种策略，并在带有黄金标注答案片段的测试语料库上进行评估，让你亲自查看召回率数据。

### 固定窗口（Fixed-window）

暴力法基线。每 N 个字符切割一次。可选择设置重叠，使得在位置 N 被切断的句子能完整出现在从位置 N - overlap 开始的下一个分块中。速度快、结果确定，但在边界处理上表现极差。应将其作为对照组使用，而非默认选项。

### 句子级（Sentence）

使用正则表达式或简单的状态机按句子边界进行分割。将一个或多个句子打包进分块，直到达到目标字符数限制。不会在单词中间截断。但仍会在段落或章节中间切断。这是许多早期 RAG 流水线的默认设置，对于没有其他结构的散文类文本是一个合理的选择。

### 递归分割（Recursive split）

由 2023 年左右的库普及的层级策略。优先尝试在最强的分隔符处分割（双换行/段落），若仍超出限制则回退到下一级（单换行），接着是句子，最后是字符。当分块大小符合预算时递归终止。对于结构不一致的文档表现强劲，因为它能根据区域自适应调整。

### 语义聚类（Semantic clustering）

对每个句子进行向量化。将共享同一主题中心点的连续句子进行聚类。只要与中心点的实时相似度低于阈值就进行切割。边界反映的是语义而非字符数。构建速度较慢且依赖嵌入模型，但对段落内部切换主题的文档具有较强鲁棒性。

### 结构化 Markdown 标题（Structural markdown headers）

适用于具有显式结构的文档（Markdown、reStructuredText、RFC 风格编号章节等），在标题边界处进行切割。每个分块包含标题及其下方所有内容，直到遇到同级或更高级别的下一个标题为止。每个主题的分块最小，但仅适用于格式规范的语料库。

### recall@k 如何衡量边界选择

带有黄金标注的查询包含了答案片段在源文档中的精确字符偏移量。分块后，你只需问一个问题：检索器返回的前 k 个分块中，是否有任何一个与黄金标注片段存在重叠？如果有，该查询的 recall@k 为 1。如果没有，则为 0。在整个查询集上求平均值。对每种策略运行相同的评估，其分数差异就能告诉你哪种边界策略最适合你的语料库。

## 构建实现

`code/main.py` 实现了以下功能：

- `fixed_window(text, size, overlap)` - 基线实现。
- `sentence_chunks(text, target)` - 简单的句子打包器。
- `recursive_split(text, separators, target)` - 层级递归逻辑。
- `semantic_chunks(text, similarity_threshold)` - 基于确定性模拟嵌入的中心点聚类算法。
- `structural_markdown(text)` - 感知标题的分割器。
- `mock_embed(text, dim)` - 基于哈希的嵌入方法，使循环可在离线环境下运行。
- `DenseIndex` - 与 Phase 19 Track B 混合检索课程中使用的数据结构一致。
- `eval_recall(strategy, corpus, queries, k)` - 对比评估循环。
- 一个 `main()`，用于在所有测试策略上运行评估并打印 recall@k 表格。

运行方式：

```bash
python3 code/main.py
```

输出为一个小型表格，每行对应一种策略，每列对应一个 k 值。句子级策略在结构化测试集上表现不佳。结构化 Markdown 策略在 Markdown 测试集上胜出。递归分割在混合测试集上表现稳健，因为其具备自适应能力。语义聚类在缺乏有效结构线索的散文测试集上表现最佳。

## 表格无法隐藏的失效模式

**孤立句子。** 句子打包可能产生遗漏主题句的分块。这会导致嵌入向量指向错误的聚类簇。

**符号中间截断。** 在代码或 YAML 中使用固定窗口会将标识符一分为二。这两部分嵌入后会变成噪声。

**仅含标题的分块。** 结构化 Markdown 可能会生成仅包含 `## Title` 的分块。请过滤掉这些分块，或将下一个分块的首段附加过来。

**语义漂移。** 当语料库主题高度统一时，语义聚类可能导致过度切割。一个 5000 字符的分块会将大量具体答案压缩进一个弥散的嵌入向量中。建议将语义方法与硬性字符上限结合使用。

**过期的嵌入向量。** 语义聚类依赖嵌入模型。如果你更换了模型，分块也会随之改变。应将分块模型与检索模型解耦锁定，或同步重建索引。

## 不运行基准测试如何选择默认策略

有三个属性决定了新语料库的默认分块器选择。

| 属性 | 取值 | 默认策略 |
|----------|-------|---------|
| 文档类型 | 无结构的散文 | 递归分割，目标长度 800 |
| 文档类型 | Markdown / RFC / API 文档 | 结构化 Markdown |
| 文档类型 | 代码 | 感知 AST（超出范围；见 Phase 19 课程 02） |
| 段落长度 | 长段落，单一主题 | 句子级，目标长度 500 |
| 段落长度 | 短段落，多主题混合 | 语义聚类，阈值 0.6 |

如果拿不准，请选择递归分割。它是表现最强的单一策略基线。

## 生产应用

生产环境最佳实践：

- 在上线新流水线前务必运行评估；不要盲目信任库自带的默认策略。
- 每次更换嵌入模型或调整语料库构成时，重新运行评估；获胜策略高度依赖语料库。
- 将策略名称持久化存储在每个分块的元数据中，以便后续排查性能回退问题。

## 练习

1. 添加第六种策略：基于 token 的窗口分割，使用 `tiktoken` 替代字符计数。在同一测试集上与固定窗口策略进行对比。
2. 在散文测试集中注入 30% 的代码块。重新运行评估表格。解释为何除结构化 Markdown 外，所有策略的召回率都会下降。
3. 将确定性模拟嵌入替换为你项目实际提供商的嵌入模型。测量语义聚类策略的召回率变化量。报告各策略间的分数差距是扩大还是缩小了。
4. 为每个分块添加一个 `summary` 字段：一句话的中心点描述。将摘要追加到分块正文后重新运行评估。测量召回率的提升幅度。

## 关键术语

| 术语 | 常见说法 | 实际含义 |
|------|-----------------|------------------------|
| Recall@k | “我们是否找到了正确的分块？” | 在前 k 个分块中至少有一个与黄金标注答案片段重叠的查询占比 |
| Chunk overlap | “滑动窗口” | 将上一个分块的最后 N 个字符重新包含到下一个分块中 |
| Structural splitter | “感知标题的分块” | 在 H1/H2/H3 标题边界处切割；标题文本本身属于分块内容的一部分 |
| Semantic chunker | “感知主题的分块” | 对句子向量化，按中心点相似度聚类，在语义发生漂移时切割 |
| Centroid drift | “主题切换” | 当前累积均值与下一个句子之间的余弦相似度跌破设定阈值 |
